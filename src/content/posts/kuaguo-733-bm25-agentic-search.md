## 一、核心观点

### 1. BM25 本身没变，变的是一个强大得多的新用户

Jo Kristian Bergum 一开场就把论点钉死了：BM25 是一个有三十年历史的词汇评分函数，它「并没有变，还是原来的评分函数」，真正发生变化的是使用它的人。过去的搜索用户是人类，敲两三个词、扫一眼十条蓝色链接；现在的用户在 Agent 循环里，拥有大量内置在参数化模型里的隐式知识，了解实体、公司、日期和产品，打字更快、读得更快、还能反复重构查询。这三点叠加，让 BM25 这类简单工具「变得更强大」。原话是：「BM25 并没有变。它还是原来的评分函数，但这里的变化其实是我们迎来了更强大的使用者。」

### 2. Agent 式搜索的定义：发生在 Agent 循环内部的搜索

Bergum 给出的定义非常克制：「Agent 式搜索，本质上就是在 Agent 的循环内部进行的搜索。」也就是说，Agent 正在完成某个任务——写代码、做深度研究——过程中产生了信息需求，这个信息需求需要用检索来满足，而检索是嵌在任务循环里的一步，而不是一个独立的前台产品。要搭好这套系统，他认为至少要三样东西：一个能力足够强、能调用工具并构建查询词的模型；一套围绕模型搭建的评测框架（harness）；一种把检索能力暴露给模型的方式（工具调用或代码模式），此外还需要一个能在数十亿规模文档集上高效跑的检索引擎。

### 3. BM25 的名字与本质：Best Match 25，一个纯评分函数

BM25 的含义是「Best Match 25」——当年研究人员做了一大批不同实验，第 25 号实验效果最好，于是留下这个名字。它的本质就是一个评分函数：给定一个查询词和一篇文档，通过查询词与文档词之间的交互算出一个分数，希望这个分数能代表文档相对于该查询的相关度。工程上，检索就是把所有文档拿来逐篇打分、取出 Top-K，而过去三四十年信息检索领域最感兴趣的方向之一，就是如何加速这种 Top-K 检索。Bergum 强调 BM25 本身只是评分函数，加速 Top-K 是另一层工程问题，两者要分开看。

### 4. 过去的评估范式已失效：十条蓝色链接不再说明问题

在传统信息检索里，大家习惯的评估方式是「看十条蓝色链接、扫一眼、算几个指标」，再比一比谁高谁低。Bergum 说这套东西现在基本不管用了，因为 Agent 非常强大，它敲出来的查询词比人类多得多——它可以重构查询、连续发起多轮搜索、做查询扩展，做各种各样人不会做的操作。因此单次查询、单份排序列表上的指标，「意义已经没那么大了」。取而代之的是端到端视角：模型有没有完成交给它的任务，比如在问答场景里，「它有没有答对」。

### 5. BrowseComp+ 揭示了真正的瓶颈：不是推理，而是检索与查询组织

Bergum 最喜欢的基准测试之一是 BrowseComp+，一个去年发表的深度研究基准，含约 830 道题，题目像酒吧问答游戏里的长谜语，每题都有标准参考答案，端到端准确率就是配了搜索工具的模型能不能答对。协议很简单：模型只拿到一个叫 search 的工具，接收查询字符串、返回摘要片段，语料大概十万篇网页文档——规模其实很小。关键发现是：如果人工把回答所需的证据文档直接塞进上下文窗口，准确率非常高，连 GPT-4 都能答得很好，「所以瓶颈不在推理能力」；但一旦给模型配上测试框架和检索工具，准确率就掉下来了，掉的原因正是它组织查询的能力，以及检索器本身的检索质量。

### 6. 上下文窗口像一张软盘，所以永远需要检索

Bergum 用了一个很有意思的怀旧比喻：把上下文窗口比作软盘。一张软盘大概能装 1.4 兆字节，而现在模型在质量开始下降之前，按他的看法大约能处理 35 万个 token——「差不多就是一张软盘的数据量」。他的推演是：就算我们实现了 AGI、有了完全不犯错的完美模型，你依然受限于这个只有一张软盘大小的窗口，你仍然必须决定「往那个上下文窗口里放什么」。这是检索在这套体系里不可替代的根本原因——检索系统的核心任务，就是从海量文档中把真正值得放进上下文的信息抓出来。

### 7. 精准匹配为什么依然有效：embedding 表达不了 SKU 和邮编

面对这种新用户，BM25 反而更厉害的三个理由：第一，用户有通识知识、打字更快、说得更具体；第二，精准匹配依然有用，因为模型知道人名、实体、邮编、SKU 这类具体标识，而这些「很难用 embedding 模型来表征」，embedding 会把所有 token 编码到一个固定词表里；第三，它相对便宜——有些 embedding 模型有 80 亿参数，为了编码文本还得为此搭一整套推理基础设施。此外 BM25 简单、工具链成熟、拿来就能用，更重要的是「模型也很容易去检查结果」，因为它匹配的是字面上的词和短语，模型能理解为什么某种查询写法会返回那样的结果，从而反过来重构查询。

### 8. 新范式：把检索结果放进文件系统工作区，让 Agent 用 Grep 探索

Bergum 认为最值得兴奋的方向，是把检索出来的结果当成给 Agent 看的「SERP」（搜索引擎结果页），并把它们放进一个工作区；如果把这个工作区组织成文件系统，就能用上「跟技能相关的那套机制」实现渐进式呈现——先给模型看文档标题和一小段摘要，模型再决定「我需要读更多这篇文档的内容」。当它这么做时，它可以使用自己本来就非常擅长的基础工具：grep、ripgrep 以及各种管理上下文的操作。这样就能兼得沙盒基础设施、检索基础设施、虚拟文件系统和 bash 的好处。他的另一个观察是：所有前沿大模型公司都在针对写代码、bash 和工具调用来优化模型，把端到端任务放在这条发展轨迹上，每出一个新模型你都知道它在这方面会更强。最后的收束是四个 takeaway：出现了更强的新用户；「你指的是哪个 BM25」；BM25 之所以对 Agent 式搜索有效，是因为它对模型可解释、能和 Grep 组合（两者都是字面匹配）；以及简单原语可以形成非常强大的 Agent 式检索范式。

## 二、关键问答

Q: BM25 已经三十年没变，为什么现在突然重新变强？
A: 因为变的是用户，不是评分函数。Bergum 反复强调「BM25 并没有变，它还是原来的评分函数」。以前的使用者是人类，只敲几个词、看一眼链接列表；现在的使用者是 LLM 驱动的 Agent，它拥有大量常识、了解实体与日期，打字更快、能一口气写出非常长的查询，还能连续重构查询。一个强得多的用户，把 BM25 这种简单原语的价值重新放大了。

Q: 到底什么是「Agent 式搜索」（Agentic Search）？
A: Bergum 的定义是：「Agent 式搜索本质上就是在 Agent 的循环内部进行的搜索。」你有一个正在执行任务的 Agent——写代码也好、做深度研究也好——过程中它产生了信息需求，为了顺利把任务搞定，它需要去检索。检索不是独立的前台服务，而是任务循环里的一步。这也是为什么传统评估方法会失准：评估对象不再是一次查询，而是一整条任务轨迹。

Q: BM25 这个名字是怎么来的？它到底算什么？
A: BM25 代表「Best Match 25」。当年有一批研究人员做了大量不同实验，第 25 号实验刚好效果最好，于是名字就这么定下来了。它的本质是一个评分函数：输入一个查询词和一篇文档，通过查询词与文档词之间的交互算出分数，用来代表这篇文档相对该查询的相关度。检索时把所有文档逐篇打分、取出 Top-K 即可。

Q: 为什么说过去的搜索评估方式已经不管用了？
A: 因为评估的对象变了。以前「你只要看十条蓝色链接、扫一眼、然后计算几个指标」，因为查询由人类发出、次数有限。但 Agent 能重构查询、能发起远多于人类的查询、能做扩展和其他操作，所以「单纯靠单次查询来评估这些系统，意义已经没那么大了」。新的标准是端到端的：在问答场景里，模型有没有答对，任务有没有完成。

Q: BrowseComp+ 是什么？它的测试协议是怎样的？
A: 它是一个去年发表的深度研究基准测试，包含大约 830 道题，题目像酒吧问答游戏里那种很长的谜语，每题都有标准参考答案，看模型和整个循环能不能给出完全一致的答案。协议很干净：模型只拿一个叫 search 的简单工具，输入查询字符串、返回摘要片段，语料库大概十万篇网页文档——按 Bergum 的说法「算是很小的」。

Q: BrowseComp+ 揭示出的瓶颈在哪里？
A: 瓶颈不在模型的推理能力。如果人工把回答所需的那几篇证据文档直接塞进模型的上下文窗口，准确率其实非常高，「连 GPT-4 也是」；但一旦给模型配上测试框架和检索工具、让它自己去搜，准确率就掉下来了。Bergum 说这是因为这是「它取决定的准确率」——取决于它组织查询的能力，以及检索器的检索质量。也就是说，检索质量会直接决定深度研究任务的端到端准确率。

Q: 上下文窗口不是已经很大了吗，为什么还需要检索？
A: Bergum 把上下文窗口比作软盘：当年一张软盘大约 1.4 兆字节，而现在模型在质量开始下降之前大约能处理 35 万个 token，「差不多就是一张软盘的数据量」。更关键的是他的推演——就算模型达到 AGI 水平、完全不犯错，你依然受限于这个窗口大小，必须决定往里面放什么。所以检索永远重要：它的任务就是从海量文档里挑出真正该进上下文的信息。

Q: Agent 的查询和人类搜索日志有什么不同？
A: Bergum 团队把 Agent 的查询和 AOL 的查询日志做对比。AOL 当年不小心公开了一大批用户搜索内容的抽样数据，那些查询都很短；他看过的更新的查询日志里，人类依然习惯用几个词去搜。但 GPT-5 是「一个能力强得多的用户」：它有通识知识，能一下子写出非常长的查询，还会用从网页搜索里学来的有用语法运算符，比如 `site:` 和短语匹配。他称这是一种全新的工作负载类型。

Q: 「你指的是哪个 BM25」——这句话在说什么？
A: 在说实现和参数的差异极大，不能笼统地说「BM25 行不行」。BM25 本质上只有两个超参数，控制评分函数的不同方面，但 BrowseComp+ 那篇论文里用的参数「并不足以应对这种长文档」，导致 BM25 这个标准基线在那个基准上做得非常糟糕。当更花哨的技术（比如 embedding 模型）拿这种弱基线去比，就会显得比实际更好。Bergum 说在那个特定基准上，参数选择对整体准确率的影响相当大。

Q: 为什么精准匹配（exact match）对 Agent 依然重要？
A: 因为模型知道人名、实体、邮编、SKU 这类非常具体的标识，而这些信息「很难用 embedding 模型来表征」，embedding 会把所有 token 编码进一个固定词表。BM25 的字面匹配恰好擅长处理这类东西：简单、便宜、生态成熟、拿来就能用。而且它可解释——模型能看懂为什么某个查询返回了这些结果，因为匹配的是字面上的词和短语，这能帮它在一定程度上重构查询。

Q: 把检索结果放进文件系统工作区，具体怎么做？
A: 把检索出来的文档当成给 Agent 看的 SERP，放进一个工作区；如果把工作区组织成文件系统，就能实现渐进式呈现——先把文档标题和一小段摘要给模型看，模型判断「我需要读更多这篇文档的内容」，然后去读。这时它用的是自己本来就非常擅长的基础工具：grep、ripgrep 以及各种上下文管理操作。Bergum 认为这能兼得沙盒基础设施、检索基础设施、虚拟文件系统和 bash，是融合当下所有新范式的一种巧妙做法。

Q: 为什么说把任务放在「写代码 / bash / 工具调用」这条轨迹上很聪明？
A: 因为所有前沿大模型公司都在针对写代码、bash 和工具调用来优化它们的模型。你把端到端任务设计在这条发展轨迹上，就意味着每当出来一个新模型，你就知道它在这方面也会更强——不需要你改架构，模型升级本身就是收益。Bergum 开玩笑说「可能等到我们实现 AGI 的时候，他们直接用浏览器就行了，我们走着瞧」，但目前这是搭检索基础设施和整套 Agent 式搜索体验的非常强大的方式。

Q: 传统 IR 里的 NDCG 为什么衡量不了 Agent 式搜索？
A: 传统信息检索的范式是「只有一个查询、一份排序列表、算一下 NDCG，然后比一比」。但 Agent 可以重构查询、发起更多查询、做扩展，还能做各种各样不同的操作，单一排序列表根本描述不了这条轨迹。所以 Bergum 说「很多经典的信息检索评估现在差不多失效了」，取而代之的是去看模型能不能完成交给它的任务——比如问答场景里有没有答对。

Q: Hornet 在做什么？他们怎么定位 BM25？
A: Hornet 在为 Agent 搭建检索基础设施。Bergum 说他们把 BM25 押注为最基础的底层原语之一，并立下愿景：要做「评估 BM25 最好、最高效的方式」，因为他认为这是一个非常强大的底层原语。他们做了一张单节点、同硬件、一亿篇网页文档的对比图，把几款匿名引擎和 Hornet 放在一起比吞吐与延迟，结论是 Hornet 的实现比其他引擎高效得多，花同样的钱能跑出更高的吞吐量——对正在为网页搜索搭基础设施的公司来说，这意味着省下一大笔钱。

Q: 这场演讲希望听众带走什么？
A: 四个观点。第一，出现了一位新用户：更强大、打字更快、阅读更快、能重构查询，而且拥有大量通用知识，这让 Grep 和 BM25 这类简单工具变得更强大。第二，「你指的是哪个 BM25」——实现和参数上都是有差异的，必须考虑这一点。第三，BM25 对 Agent 式搜索有效的关键原因是它对模型可解释，并且能和 Grep 结合起来用，因为两者做的都是字面匹配。第四，这种组合本身就是一种非常强大的 Agent 式搜索范式。

## 三、备忘

**核心术语**
- BM25：Best Match 25，词汇级评分函数，只有两个超参数（常见实现中为 k1 与 b）；BM25 常作为信息检索研究的标准基线。
- Agentic Search / Agent 式搜索 / Agent 式检索：在 Agent 循环内部进行的搜索。
- Top-K 检索：把全部文档逐篇打分后取分数最高的 K 篇；加速 Top-K 是 IR 领域持续三四十年的工程主线。
- NDCG：传统 IR 排序质量指标；对可重构查询、多轮检索的 Agent 轨迹基本失效。
- Context window / 上下文窗口：Bergum 比作软盘（约 1.4 MB），模型质量下降前约 35 万 token。
- 参数化知识（转录中作「影视知识」）：内建于 LLM 权重中的实体、公司、日期等常识。
- SERP：搜索引擎结果页；在 Agent 语境里指检索器返回给模型的结果集合。
- 渐进式呈现（progressive disclosure）：先给标题与摘要，模型再按需读取全文。
- 精准匹配（exact match）：BM25 与 Grep 的共同基础，都是字面匹配。

**工具与产品**
- Hornet.dev / Hornet：Bergum 的公司，为 Agent 搭建检索基础设施，主推高效 BM25 实现。
- Grep / ripgrep（转录中作 "rep grabs"）、`site:` 运算符、短语匹配。
- AOL 查询日志：当年意外公开的人类搜索抽样数据，用作与 Agent 查询的对照基线。
- 沙盒基础设施 + 虚拟文件系统 + bash：与检索基础设施融合的新范式。
- 转录里的 "z-arc" 疑为 z 系列工具（如 zgrep/zcat），Whisper 误转，存疑。

**基准测试**
- BrowseComp+（转录中作 Broscomfate / Broscom非 / BrowseCom非）：深度研究基准，去年发表，约 830 道谜语式题目，每题有标准答案；协议只给模型一个 search 工具，语料约十万篇网页文档。
- BrowseComp+ 结论：证据文档直塞上下文 → 准确率很高（连 GPT-4 也是）；配上检索工具 → 准确率下降，瓶颈在查询组织能力与检索质量。
