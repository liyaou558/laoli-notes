## 一、核心观点

### 1. 从 2023 年的 prompt 工程师热，到今天的「harness 已死」之问

节目开场的对照极具戏剧性：2023 年科技行业最火的职位头衔是 prompt 工程师，人人都在讨论怎么把指令写得更好；而到了今天，问题反过来了——模型自己越来越会写代码、会读代码库、会自己跑测试，那么专门为模型服务的 agent harness 是不是就该退出历史舞台？Jediah Katz 的答案既不是「是」也不是「否」，而是一条更精确的切分线：harness 里那些用来补模型编程短板的功能，确实会被模型学会然后删除；但 harness 还有另一个不可替代的职责，就是把 agent 带进模型尚未掌握的全新任务领域。这条切分线决定了 harness 工程的长期价值在哪里。

### 2. 数据飞轮让 harness 自我淘汰，这是设计出来的结果

在 Cursor 的经历被 Jediah 用来解释「过时」这件事的机制。他用 GrindSwarm 举例：这套 harness 让 Cursor 从零开始做出一个浏览器，而这个过程本身产生了大量高价值的编程数据；更难的工程任务带来更多编程轨迹，模型在这些数据上继续训练，学会了原本需要 harness 显式教给它的本领——怎么摸清一个陌生代码库、怎么在长任务里持续工作、怎么运行测试并解读失败。他表示：「这些本领，模型现在自己就会了。」于是下一版 harness 就可以把旧功能删掉，把复杂度让渡给模型。换言之，一个好的 harness 不是永久的脚手架，而是把自己写进模型权重的教练机。

### 3. 新任务到来时，删掉的防护又会被加回来

最有意思的转折出现在 Grokbot。Cursor 因为模型能力提升，一路删掉了不少 prompt 和防护措施；但转到知识工作场景后，团队发现自己反而在往回加东西。「但有意思的是，在 Grokbot 里，我们发现自己反而把很多这些东西又加了回来，加入新的 prompt，新的防护措施。」原因很朴素：Grokbot 要处理邮件、要与人沟通、要记住用户的工作方式和偏好，这些任务的失败成本与代码任务完全不同——代码跑错可以看测试，邮件发错就收不回来了。因此安全网、确认步骤、风格约束、记忆结构重新变成必需品。这也印证了那条切分线：模型没学会的地方，就是 harness 要重新搭台子的地方。

### 4. 要让 agent 真正自主，它就必须离开笔记本

agent 任务的时间尺度在肉眼可见地拉长——从最初的几分钟，延长到几小时、几天甚至更久。一台笔记本电脑会合盖休眠、会断网、会被人带走，因此把长任务挂在本地是不可靠的。Jediah 的结论直接：「agent 必须在云端运行，你才能真正有一个能自主工作的同事。」这条判断把 harness 的设计重心从「本地工具编排」推向「云端运行时」：持久化状态、断点续跑、任务队列、资源隔离，这些原本属于基础设施团队的问题，变成了 harness 工程师的日常。它也解释了为什么节目里讨论的重心不是某个巧妙的 prompt，而是运行环境与信任边界。

### 5. 评测分数差不多，成本和速度仍能拉开明显差距

一个很容易被忽略的工程现实：不同 harness 在编程评测上的分数并没有显著差异，但完成同一个任务的成本差别明显。原因是缓存命中率、token 使用效率、以及模型搭配策略（什么环节用大模型、什么环节用小模型）的差异会被任务规模放大。Jediah 说团队在做完这些优化后，Grokbot 的成本下降、速度加快，而质量没有受到影响——这几乎是工程学里最理想的那类胜利。他的总结是：「你越多地用 agent 来工作，拥有最高效的 harness 对你就越有价值。」当调用量足够大，harness 的效率差异就从「省钱」升级成「能不能用得起」。

### 6. 信任与安全是云端 agent 的隐形门槛

云端自主运行意味着权限放大，因此 Jediah 反复强调信任与安全的工程化。节目里给出的一个具体画面是：[10:39] 报 bug 之后，云端 agent 自动修复并监控上线——注意这里的完整链路不止「修复」，还包括部署与上线后的监控。这种端到端闭环让 agent 从「建议者」变成「执行者」，但也要求 harness 设计出一整套边界：它能改什么、不能改什么，什么时候必须请人确认，出错时如何回滚。安全不是一个附加的护栏，而是决定 agent 能否被授予自主权的前提条件。

### 7. 预测：6 个月内 90% 的 agent 工作会离开笔记本

Jediah 给出了一个时间明确、比例明确的预测：6 个月内，90% 的 agent 工作会在笔记本电脑以外运行。这不是一个关于本地工具变差的判断，而是关于 agent 工作形态演化的判断——真正自主的 agent 必须朝云端方向发展，因为自主性天然要求跨越设备在线状态和人的作息。这个数字的价值不在精确度，而在它给出的方向感和紧迫感：如果这个比例真的实现，那么今天围绕本地 IDE 和本地终端构建的 harness 假设，都会在半年内被重写。对工程师而言，这意味着把注意力从「更好的本地体验」转向「更好的云端运行时」。

## 二、关键问答

**Q：** Agent Harness 真的会死吗？
**A：** 不会整体死亡，但会持续被掏空一部分。Jediah 划出的界线是：凡是用来补模型编程短板的功能——教它读代码库、维持长任务、运行测试——都会随模型能力提升而被删除；harness 的长期价值转移到「把 agent 带进模型尚未掌握的新任务」，以及云端运行时、信任与安全这些模型本身无法自我提供的部分。

**Q：** 数据飞轮具体是怎么让 harness 「过时」的？
**A：** 一个正反馈是：harness 帮 agent 完成更难的工程任务，任务产生大量高质量编程数据；模型吃下数据后学会原本靠 harness 支撑的能力，harness 便可删掉旧功能。GrindSwarm 让 Cursor 从零做出浏览器为例，所以「过时」是 harness 成功把能力转移进模型的结果。

**Q：** 为什么 Cursor 删掉的防护，在 Grokbot 里又加回来了？
**A：** 因为任务性质变了。代码任务的错误可以由测试和编译暴露，知识工作任务的错误往往是不可逆的——邮件发出去就收不回，行程订错要付出真实成本。Grokbot 要处理邮件、与人沟通、记住用户的工作方式，所以团队重新加入新的 prompt 与防护措施，用确认步骤和风格约束把失败成本压下来。

**Q：** Grokbot 被描述成「能自主工作的同事」，它和普通助手差在哪？
**A：** 差别在时间尺度与主动性。普通助手响应一次请求，任务以分钟计；Grokbot 承接的是几小时到几天的长任务，需要自己规划、自己检查、在没人盯着的时候继续推进。这要求它记住用户的工作习惯、在多轮交互中保持上下文，也要求它有稳定的运行环境——也就是为什么「云端运行」不是可选项而是前提。

**Q：** 为什么 agent 一定要在云端跑，本地笔记本不行？
**A：** 因为笔记本会休眠、会断网、会被人合盖带走，而 agent 任务已经从几分钟延长到几小时、几天甚至更久。挂在本地的长任务一旦中断，前面积累的状态就可能丢失。Jediah 的说法很直接：agent 必须在云端运行，你才能真正有一个能自主工作的同事——自主性的物理前提是持续在线。

**Q：** 评测分数接近的 harness，差距到底体现在哪里？
**A：** 体现在单位任务的成本与速度。Jediah 指出不同 harness 的编程评测分数没有显著差异，但每个任务的花费差别明显，来源是缓存优化、token 使用效率、以及大小模型的搭配策略。Grokbot 在做完这些优化后成本下降、速度变快而质量不变。用量越大，这种效率差距越会转化为可行与不可行的分界。

**Q：** 云端 agent 的信任与安全问题怎么解？
**A：** 节目给的样本是完整闭环而非单点能力：[10:39] 报 bug 后，云端 agent 自动修复并监控上线。要做到这一点，harness 必须明确权限边界（能改什么、不能改什么）、设置人工确认节点、并保证出错可回滚。安全不是事后加的护栏，而是决定能否把自主权交给 agent 的前置条件。

**Q：** 他对 agent 工作形态的预测是什么？
**A：** 6 个月内，90% 的 agent 工作会在笔记本电脑以外运行。这个预测的落点是方向而非精确比例：真正自主的 agent 必须走向云端，因为自主性要求跨越设备在线状态与人的作息。若预测成真，今天围绕本地 IDE 与本地终端建立的 harness 假设会在半年内被重写，工程重心将转向云端运行时。
