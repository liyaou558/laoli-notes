一个金融分析 Agent，跑完一轮搜索、推理、写报告，看起来挺像回事。然后你打开它的报告，看到一句话：「有 116% 的分析师持某些观点。」

这就是这一集的核心场景。Laurie Voss 用 Claude Agent SDK + Phoenix 搭了一个金融分析 Agent，从「看着不错就上线」一路做到「进 CI 当测试」，中间踩的坑几乎覆盖了所有团队做 Agent 评估会踩的坑：不知道从哪下手、把评估写成了走形式、裁判自己也不靠谱、分数涨了但产品并没有变可靠。

## 一、核心观点

### 1. 116% 的占比，暴露的不是数据错误而是推理错误

那份特斯拉报告把两次网页搜索里、并非来自同一数据集的比例拼在一起，算出「分析师建议比例合计 116%」，然后信心十足写进结论。关键在于：搜索结果的每一条本身都没错，错在 Agent 没有能力对来源做一致性推理——它不会发现「这几组百分比的分母不一样」。所以这类 bug 用单元测试、用格式校验、用关键词检查全都抓不到。只有回看 trace，看着它一步一步怎么拼出来的，才知道错在哪一步。

### 2. Trace 是日志，eval 是对日志做测试，两者不能互相替代

Laurie 给的定义极简：Trace 是「记录 Agent 每一步做了什么」，eval 是「对这条运行记录跑断言」。没有 trace，你不知道失败发生在搜索、推理还是生成环节，只能对着最终报告猜；没有 eval，你有几百条 trace 也只能靠肉眼看，回归无从谈起。这一集里有一处很实在的建议：写第一条评估之前，先从头到尾读十几条完整追踪记录。不是为了写代码，是为了知道「错」长什么样。

### 3. 新模型几周就来一次，没有评估你根本不敢升级

现在模型发布节奏是几周一个大版本。团队面临的现实问题不是「新模型是不是更强」，而是「换过去会不会把我已经修好的地方弄坏」。如果没有一套固定的评估集，升级就变成一次纯赌博——上线后靠用户反馈发现回归，代价极高。评估在这里的作用不是给模型打分排名，是给你一个可重复的安全网，让「换模型」从冒险变成一个可以按流程做的决定。

### 4. Agent 最麻烦的错误类型：错得很自信

Laurie 把「confidently wrong」列为最棘手的问题之一。传统软件出错会崩、会抛异常、会给你一个空值；Agent 出错会给你一段语法完美、语气笃定、结构完整的报告。下游的人和系统都没有理由怀疑它。这直接决定了评估设计的重点：不能只测「输出格式对不对」，必须测「结论有没有被证据支撑」。可惜大部分团队的第一版评估恰好只测前者，因为那最容易写。

### 5. 改 1 行 Prompt，修好了你测的那一项，也仅此而已

这是全场最有价值的一组数字。改进 Prompt、要求 Agent 必须给出明确建议后，可操作性评估从 16 份里 5 份通过，跳到 48 份全部通过——看起来是完美修复。但同一批报告的忠实度只从 16 份里 2 份，变成 48 份里 3 份。也就是说：「必须给建议」这条指令，逼着模型把「持有」这种安全答案换成了具体建议，但完全没解决它编造数据的老毛病。Laurie 的原话是：「只改了 prompt 里的 1 行，就解决了我们衡量的那个问题，但没解决 agent 瞎编的问题。」

### 6. 一个「上帝评估器」看着省事，失败时说不清哪里错

把准确性、语气、完整性、格式、业务规则全塞进一个裁判，让它输出一个总分，是很自然的偷懒方式。问题是当它判失败时，你不知道该改 Prompt、改检索、还是改输出模板——信息量为零。Laurie 的做法是按维度拆开：你要测多少个维度，就拆成多少个评估器，每个只回答一个窄问题。然后再做一层分级：哪些是发布底线（不过就不能上），哪些只是改进目标（记录但不阻塞）。

### 7. 裁判本身也是分类器，必须拿人工判断来校准

大模型裁判不是天然可信的。Laurie 用人工标注的黄金数据集跟裁判对照，结果包括他自己在内——有时人并没有严格按自己亲手写下的标准在判断。这一步很反直觉但很关键：先验证裁判，再用裁判验证 Agent。另外他强调评估指标要选对：他们一度让「正确性裁判」判那 16 份报告，结果全被判错，真正原因是那个裁判无法核实「最新数据」，指标本身选错了。选对评估，比把评估调好更重要。

### 8. 分数变好不等于变可靠：Haiku 5.5 的三倍与四倍

换到 Haiku 5.5 后，忠实度是 Haiku 4.5 的 3 倍多，但成本变成 4 倍。同时出现一个新现象：它几乎每次都建议持有。建议一致性上去了，可操作性意义上的价值反而下降——「做到这一点的办法就是每次都选同一个答案。」这是评估里最容易被忽略的一课：单一指标改善可以靠退化成保守策略换来。所以必须多维度同时看，而且要盯着分布，不只看通过率。

## 二、关键问答

**Q：为什么不能靠「看着不错」就上线？**
A：因为 Agent 的错误不会以崩溃的形式出现。它给你的是一份结构完整、语气笃定的报告，人没有理由怀疑。上线之后你才发现问题，代价是信任和返工。Laurie 的起点就是这个：改完 Prompt 后他担心的是回归——之前修好的地方会不会又被弄坏。没有评估，这种担心只能靠猜。

**Q：为什么要把评估接进 npm test 和 CI？**
A：评估如果只是一个手动跑的 notebook，它一定会烂掉。接进 npm test 和 CI 意味着每次改动都自动跑，回归在合并前就被拦住。这一集最后落地的东西很朴素：把股票代码检查和可操作性检查放进 npm test——不是最聪明的评估，但是每次都会跑的那两个。

**Q：Trace 和 eval 的区别到底是什么？**
A：Trace 是日志，记录一次运行里搜索了什么、推理了什么、生成了什么，每一步的输入输出都在。Eval 是对这条运行记录做测试，用代码或裁判给出通过或不通过。前者是素材，后者是断言。没有 trace 的 eval 是黑盒打分，没有 eval 的 trace 是一次性侦探工作，看完就没了。

**Q：一次 Agent 运行大概包含哪些步骤？**
A：以这个金融分析 Agent 为例：先上网搜索最新数据，然后推理（把搜到的数字组织成结论），再生成一份给分析师看的报告。三段里每一段都可能出错，而且错误会传播——搜索拿到不同数据集的比例，推理阶段没有察觉，生成阶段就写成 116%。这也解释了为什么必须看 trace，而不能只看最终输出。

**Q：写第一条评估之前该做什么？**
A：从头读十几条完整的追踪记录。Laurie 的原话意思是：先做错误分析，再做评估工程。你要先知道真实的失败有哪些类型、各占多少比例，才知道该测什么。跳过这一步直接写评估，写出来的通常是你想象中的失败，而不是实际发生的失败。

**Q：哪些检查应该用代码写，而不是用大模型裁判？**
A：确定性的、几毫秒能算完的，一律用代码。股票代码对不对、格式合不合规、数字能不能加总、字段有没有缺——这些用正则和断言就够了，快、免费、可解释。把这类东西交给大模型裁判，纯属浪费钱还引入不确定性。裁判应该只用在「需要判断语义」的地方。

**Q：什么情况下不该用大模型裁判？**
A：当你需要的是「核实事实」而不是「判断表达」的时候。他们那次让正确性裁判去判 16 份报告，结果全部判错，原因是裁判无法核实最新数据——它没有联网能力，只能凭训练时的记忆判断真假。这类任务要么给裁判工具，要么换成能核实的检查，否则裁判给出的只是自信的猜测。

**Q：为什么不要一个「上帝评估器」？**
A：因为它失败时无法定位。同时检查准确性、语气、完整性、格式、规则，输出一个失败，你不知道该改哪里。拆开之后每个评估器只回答一个窄问题：「这个数字有出处吗」「建议明确吗」「格式对吗」。窄问题的裁判也更准，因为你给它的标准更具体，它需要判断的空间更小。

**Q：怎么区分发布底线和改进目标？**
A：Laurie 把评估分成两类：一类是不过就不能发的硬门槛，比如股票代码错误、数字自相矛盾；另一类是记录但不阻塞的改进项，比如语气、详略。这个分级很重要，因为如果把所有评估都设成阻塞，团队会因为一个语气不达标而卡住发布，最后大家的解决办法是把评估删掉。

**Q：改 Prompt 后指标大涨，为什么不能庆祝？**
A：因为可能只是修好了你恰好测的那一项。他们的可操作性从 5/16 到 48/48，同时忠实度从 2/16 到 3/48——如果只看可操作性，这是一次巨大成功。所以每次改动都要跑全套评估，并且专门盯着「这次改动可能弄坏的维度」。单指标改善是最容易骗人的信号。

**Q：怎么验证裁判本身靠不靠谱？**
A：用人工标注的黄金数据集跟裁判对照，看一致率，并且看分歧的具体案例。Laurie 在这件事上很坦诚：对照过程中他发现，包括他自己在内，人有时并没有严格按自己写下的标准判断。所以校准是双向的——既修裁判，也修标准。他的判断标准很朴素：你要的是一个比另一个人来当裁判表现更好的模型。

**Q：为什么说选对评估比调好评估更重要？**
A：因为错的指标会把整个团队带向错误方向。正确性裁判那次全判错，不是裁判调得不好，是这个指标在当前条件下根本无法测量。你花几周优化一个测不准的东西，最后得到的是精致的噪声。选指标时先问：这个判断在这个信息条件下可不可能做对？

**Q：换 Haiku 5.5 之后发生了什么？**
A：忠实度是 Haiku 4.5 的 3 倍多，成本是 4 倍。同时它几乎每次都建议持有。看起来「更稳定了」，实际上是退化成了保守策略。这是评估里最经典的陷阱：一致性、安全性、稳定性这些指标，都可以通过「永远给同一个答案」来刷高。所以才需要同时看忠实度、可操作性、建议分布。

**Q：往 CI 里放什么最划算？**
A：放最便宜、最确定、最能拦住灾难的那几个。他们的选择是股票代码检查和可操作性检查——一个用代码几毫秒搞定，一个直接对应产品价值。这两个进 npm test，意味着每次提交都被验证，而不是等发版前跑一次大评估。评估体系的成熟标志不是有多少个评估器，是有多少个在自动跑。
