## 一、核心观点

### 1. 从声乐教练到 Total TypeScript：把"讲清楚"练成了职业外挂

Matt Pocock 在成为程序员之前的六年是一名发声教练：在伦敦和埃克塞特教声乐、教口音、教发声，还读了相关硕士，给戏剧学校的学生讲莎士比亚台词，给咨询公司上公开演讲课。他离开这一行不是因为不喜欢，而是"要想做到不错的水平就必须住在伦敦，而我讨厌住在伦敦"——于是为了能有一份可以远程做的工作，他自学 JavaScript 转行，2017 年前后在英国找到第一份工作（他坦承那是个对工程师需求极高的窗口期，上过几个月培训班的人也能拿到机会）。真正的杠杆来自叠加：初入行时他技术有限，却"有能力把技术知识给别人讲明白"，面试时像个"通情达理的正常人"而不是刚毕业的计算机学生。这两种能力一结合，他在几家外包公司里升职都非常快。

### 2. AI 吃掉了战术性编程，人类被推上战略层

Matt 直接引用了 John Ousterhout 关于战术性编程与战略性编程的区分，并给出自己的时代判断：**战术性编程大半已经被 AI 吃掉了，留给我们的就是把控战略**。触点是所谓"去年 12 月的那个假期"（他称之为"AI killed 的那个寒假"，Opus 4.5 刚发布，所有人休假回来拼命猛用，猛然发现事情真的开始不一样了）。他意识到可以把架构搭在 Agent 外面，让 Agent 去处理具体的知识与法——也就是战术层面的东西，而人去负责长远思考。他的课程方向也因此转向：从"怎么把 AI 放进应用里"（他承认自己压错了注）转到"在战略层能做出什么课"。

### 3. 知识越来越便宜，但智慧不会自动出现

Matt 把教学内容分成两层：一是"是什么"（语法、具体知识），二是背后的"为什么"（一套智慧）。他明确说："现在获取知识的成本非常低，你随手一查就行，我写了个 teach skill 就能教会你需要的知识——**但智慧并没有变得更容易学到**。" 他观察到线上教育从业者的营收、市场份额、心智份额都在下滑，"因为知识本身已经不再难找了"。他自己的 Total TypeScript 收入也确实掉了下来。他甚至半开玩笑地劝过：要是你之前没掌握那份智慧，哪怕有了 AI，该踩的坑还是一个都躲不掉。

### 4. Grill Me 的价值不是替你做决定，而是逼你做决定

Grill Me 是最受欢迎的一个 skill，逻辑极简：让 Agent 抓着话题不停追问你，直到把每个决定都问出来。主持人用它设计一个 API 端点时被问了 35 个问题，"压力很大也很烦人，但逼着我做了更多思考"——从"用 bearer token 还是放在 JSON 里"（后者没那么安全），一路问到速率限制是否要严格卡在"一天一千次，多一次都不行"。Matt 喜欢它的点在于：**拍板的人仍然是我**，它不像一条"把这个做出来"的斜杠命令那样把所有关键决定都替你做了；而且它常常提醒你去查一些没深思过的事（"我得去看看 POST 和 GET 的区别"）。他把这种体验比作第一份工作里和那位穿凉鞋的资深工程师讨论问题，也比作和 XState 顶级开发者在同一间屋子里工作。

### 5. 用多个会话把工作留在"聪明区"：Ralph Loops 的本质

Matt 大量借用 Dex Horthy 的"聪明区 / 笨拙区"（smart zone / dumb zone）概念：给 Agent 的上下文越多，每个 token 都在大声争夺注意力，模型就越容易丢掉事物之间的关联并犯错。在目前的顶尖模型里，他觉得表现最好的是**前 15 万个 token**——"不管上下文窗口是一百万还是更大，看的都是 token 的绝对数量"。于是问题变成：怎么把超过 15 万 token 的工作拆到多个会话里？Ralph Loops 就是他试出来的一个版本：给循环一个目标，让它做"能让我们往目标推进一步的最小改动"，然后清空上下文从头开始——严格说不是从头，因为代码库、文件系统和环境里还留着状态。配套的节奏是"白天做规划、夜晚让 Agent 干活"，最好一觉醒来代码已经写得漂漂亮亮。

### 6. Wayfinder：把复杂项目变成一张带战争迷雾的地图

如果一次盘问必然撞上 15 万 token 的天花板（比如"帮我做个 Stripe 的克隆"），就需要把深挖过程本身拆开。Wayfinder 的核心是**地图**：一切已做决策所需信息的核心集结点。地图上有像里程碑一样必须定下来的点，也有"战争迷雾"——隐约知道自己要去哪，每完成一次拷问环节就解锁更多地点，路径像一张有向无环图（DAG）。地图上每张工单可以是不同类型：拷问、调研、随手的基础设施配置。Matt 说自己某些地图上有 50 张甚至 100 张工单。他还把它用在非技术事上——规划课程，以及在自家花园里搭一间花园办公室："我们总觉得这类技能适合工程，但工程也不过就是一门专业。"

### 7. 经典软件书籍回来了，而且可以直接当"引导词"用

Matt 把规格驱动开发（"也许英语真的是最火的新编程语言"）试了很久，结果发现**按"改规格→看代码变化"的循环来跑，代码会变得更烂**："按说人是不该去看代码的，但我看了一眼，简直就是垃圾。" 问题出在反馈回路——测试套件很烂，Agent 拿到的信号就很烂，跟人一模一样。于是他翻开书架上连塑料膜都没拆的《程序员修炼之道》，里面整章讲软件熵增，而"Agent 制造软件熵增的速度比以往任何时候都要快"。他从书里挖出一批精准词汇（曳光弹开发、垂直切片、深度模块、不要超出车灯照射范围、巧合编程），在 prompt 里反复用，结果**模型开始把这些词回敬给他**，在自己的推理链里用同样的术语规划。他把这类词叫"引导词"，或用一个文学词汇：主导动机（leitmotif）。

### 8. 软件熵增正在被 Agent 加速，所以要为"每天失忆的新人"优化代码库

Matt 的比喻是《记忆碎片》：你面对的是一个每天早上醒来都不记得自己是谁的人——"这就是记忆碎片驱动开发"。人类面对烂代码库还能绕过去，一次次碰壁后慢慢形成记忆；Agent 每次都从零开始，所以**你必须为一个没有长期记忆的新人优化代码库**，目标是"做出有史以来最健康的代码库"。这也解释了为什么通用语言（Ubiquitous Language，出自 Eric Evans 的领域驱动设计）在 AI 时代突然变得极其实用：一旦 Agent 和你用同一套领域术语交流，"你能用少得多的字句描述你想改动的东西"，而且它能在代码库里一个 grep 就找到提到那个术语的函数。他甚至把 Grill Me 改成 grill with docs（他自嘲名字起得很烂），在构思应用的同时顺手建立领域语言。

### 9. 真正管用的基本功：反馈回路、垂直切片、自动化审查、可观测性

被问到"具体哪些基本功管用"时，Matt 的回答很聚焦：**让 Agent 一直在反馈回路里工作**。他吐槽 Agent 的典型毛病是水平切片——先把整个数据库建好，再写完整个应用层，再写完整个 React 组件库，最后才拼起来，"这让人抓狂，因为数据库里的东西会影响你在前端展示的内容"。对应解法就是垂直切片：做一个能立刻拿到反馈的纵向通路，再往外扩建。他还强调自动化审查——一个实现 Agent 干活，另一个审查 Agent 执行编码规范、抓出同义反复测试（测试只是把实现代码抄一遍的断言），持续提高测试套件质量。落到组织层面，第一步是**对每一个 Agent 建立可观测性**：看它在做什么、成功率和失败率是多少——"以前我们从来不可能对开发者这么做，那有点太冒犯了，但对 Agent 就应该这样。"

### 10. TDD 是为人的工作记忆优化的问题，Agent 需要的是"证明"

Matt 有自己推荐的 TDD skill，但他对 TDD 的态度是"复杂"的：TDD 针对的是**人类很小的工作记忆**——先写一个理应通不过的测试，就算你去喝杯咖啡、散个长步，回来时测试还挂在那提醒你做到哪了。Agent 不需要这个，它们的"工作记忆"比人大得多。Agent 真正需要的是反馈回路：看到自己做了什么、与代码环境如何交互。所以他的用法是"拿出符合 TDD 精神的证据"——"证明你的改动确实做到你声称做到的事，证明要是没有这处改动它就通不过"。他还点出 Agent 写烂测试的两种典型：同义反复测试，以及断言实现细节。谈到技术债（"任何随时间推移让代码库变得更难修改的东西"），他的判断是：Agent 无法做战略性思考，只盯着眼前的任务，所以**哪怕极小的代码库里，只改一行代码也可能产出垃圾**。

## 二、关键问答

**Q：你最初并不是学计算机科学的，后来怎么转的行？**
A：完全不是。在成为程序员之前的六年，我是发声教练——在伦敦和埃克塞特教声乐、口音和发声，还念了这个方向的硕士，给戏剧学校的学生讲莎士比亚台词，也给咨询公司做过公开演讲培训，我以为那就是我一辈子的职业。离开是因为要想做到不错的水平就必须住在伦敦，而我试着住了两年、非常讨厌那里，我想回到我长大的乡下。为了能有一份可以远程做的工作，我自学编程：用 JavaScript 给学生做抽认卡小工具，还做过一个网页音频分析器，能分析声音的频谱图、看产生了哪些共振峰——做得极深，跑起来卡无比。

**Q：第一份工作和 TypeScript 的渊源是怎么开始的？**
A：第一份工作在一家很小的公司，有个常年穿凉鞋、住运河船、留长发的硬核工程师（他喜欢匿名），微软收购 GitHub 那阵子他走进来几乎快哭了，他让我做的第一件事就是在 Windows 上装 CentOS 6。后来公司遇到财务困难，我跳去外包公司。那里技术栈是 TypeScript 和 React：我们给一家汽车制造商做学习管理系统，前端团队很小、后端团队在葡萄牙，后端进展神速而前端动作慢、bug 一大堆，还老是不打招呼就改接口契约。TypeScript 顺理成章地把两边衔接起来，上线后我们的速度比后端还快，最后他们因为前端太快还从我们组抽走了几个人。

**Q：你是怎么进入开源圈子的？**
A：推特上有个专门讲状态机和 TypeScript 的人叫 David Khourshid，我的职业生涯很大程度归功于他。我在第四份工作里要做一个很复杂的应用——视频通话的同时还能实时一起逛一栋房子，跨网络边界联动很多，于是用了 XState v4，效果特别成功。我琢磨怎么让它更类型安全，写了个围绕它搭建的 CLI，这引起了他的注意，我成了 XState 核心团队成员，也开始接触一批我以前从未见过的顶尖开发者。后来 David 想围绕它开一家公司（就是后来的 Stately），重筑状态图和可视化编程，那基本上是我第一份拿到美国薪酬的工作，是一次巨大的跃升。之后我去了 Vercel：负责开发者教育的是 Lee Robinson，团队里还有 Delba de Oliveira、Lydia Hallie（后两位现在都在 Claude Code 团队），我在 Jared Palmer 手下做类似角色——他后来去 GitHub 主导了堆叠式 diff，现在在 Cognition，是业界传奇。入职后正好赶上 Turbopack 发布，最初的一些文档是我写的，我也在 Next.js Conf 的发布现场；但大概两个月后，想教东西的冲动回来了，Total TypeScript 的预售直接卖爆——假设在 Vercel 拿一份收入 X，预售进来的差不多是 30 到 40 倍，太明显了，我没有别的选择。

**Q：Total TypeScript 是怎么做起来的，成绩和商业模式如何？**
A：我跟 Joel Hooks 合作——egghead 的创始人，帮 Kent C. Dodds 做过课程，是个在幕后极其成功的课程创作者，我主动联系他，他一口答应。2023 年 1、2 月上线完整课程后迅速突破七位数（100 万美元原始营收，当然里面还有成本和我俩的分成），后来总营收又突破了 250 万美元。商业模式很坦荡：我做出了这个东西，大家想学就掏钱买，希望从中得到价值，不然就申请退款，而退款期限给得很长；我也不喜欢做赞助内容。这里面很大一部分钱来自各公司的员工培训预算——这是我以前完全没有概念的市场，意识到之后我在营销里起了非常关键的作用。

**Q：AI 是怎么冲击你的教学业务的？你又怎么找到新位置的？**
A：很复杂。我教的是语法（"是什么"），但背后还有一层"为什么"——我教你知识，同时也想教给你智慧。现在获取知识的成本非常低，我写了个 teach skill 就能教会你需要的东西，但**智慧并没有变得更容易学到**，你该踩的坑还是一个都躲不掉。收入显然掉下来了。我一开始转做"怎么把 AI 放进应用里"的课程，后来清楚意识到自己压错了注，收益没达预期。转折点是去年 12 月那个假期：Opus 4.5 刚发布，大家放长假拼命猛用，回来都喊着"AI killed"。我也意识到现在的 AI 已经好到可以放心把活委托出去——在 Agent 外面搭架构，让它处理战术层面的知识与法，人负责战略。这正对上 John Ousterhout 讲的战术性编程与战略性编程的区分，而在战略层，我觉得自己是能做出一门课的。

**Q：Ralph Loops 是怎么被你想出来的？**
A：我在看 Geoffrey Huntley 做的很酷的东西，能让 Agent 循环运行并盯牢目标。我花了两三年琢磨怎么把 Agent 放进应用里，那段经历在这里帮了大忙——做带 Agent 的应用时，脑子里想的永远是数据流：怎么流进来、格式什么样、优先级怎么定、放进系统提示词还是用户提示词、状态存在哪、怎么压缩或清空它。所以转去用这套"测试脚手架"时感觉特别熟悉。Claude Code 那会儿刚出五六个月，用起来顺理成章。

**Q：你说过"以前让 Agent 干活是先定计划再一步步执行"，问题在哪？**
A：那是自顶向下的传统规划，问题在于执行过程中——甚至 Agent 自己执行的过程中——它会意识到"等等，我得干更多的事"，那这时候你怎么改计划？Ralph Loop 当时的结构大概就是一个 markdown 文件：内容留在那里，一边消耗一边不断往里补。我后来把这些串联方式都叫 loop，其实就是流程图——能从一样东西画箭头到另一样东西就能叫循环，尤其是有一条回路连回来的时候；你也可以叫它工作流，我会管它叫**有限状态机**：基于流程和状态，最底下的 Agent 把事件反向调回顶层。

**Q：规格说明书和工单是怎么衔接的？**
A：我需要两种文档：一份说明你要去往何方的文档——我过去叫它 PRD，现在叫它**规格说明书**（写明什么时候算到终点）；然后把这份规格说明书拆成一个个任务工单，一次 session 一个工单。所以就是两个很简单的 skill：先出规格说明书，再出工单。你把之前那次 Grill Me 会话变成一份规格说明书，它能管 30 到 40 个工单，规模非常庞大的整块工作全挂在它下面。核心流程是：先盘问深挖 → 变成规格说明书 → 对着工单跑实现循环，直到搞定一大块工作。

**Q：skill 是怎么变成分发机制的？现在的量级有多大？**
A：我先给自己搭流程：给定制视频编辑器、大代码库、几个开源项目搭小循环和小流水线，有时干脆停掉切回默认配置，区别特别大。所谓 skill 其实就是放在你电脑某个位置的一个 markdown 文件夹：有 Agent 自己可以调用的（模型调用的 skill），也有 Agent 不知道、你可以自己调用的（用户调用的 skill）。4 月我在 AI Engineer London 做了一场演讲叫"软件基本功依然重要"，播放量大概到了 120 万次；里面的 skill 集在转录里说 star 到了"23 万"、是全球 star 第二多的 skills 仓库（注：23 万这个数字可疑，更可能是 2.3 万 / 23k 量级，待核）。我起初只是直接传上去然后去忙别的课，回头一看 star 数比我做过的任何东西都多。

**Q：写这些 skill 的第一原则是什么？为什么一个"很小"的 skill 效果这么好？**
A：我想的是：大家用这些 skill 时肯定会去改动、调试它们，那我怎么做出最简单的一套，让大家非常容易看懂和审查？怎么才能让更多人在工作中真正用起来？所以 Grill Me 的设计非常小，却带有一种奇妙的涌现行为——模型会跳出固有思维去琢磨，然后抛出各种想法。这个思路我最初是从 Claude Code 团队的一个人（转录作"Tarik"，疑为 Thariq，待核）那儿学来的：让 Agent 来面试你，你就会看到更好的结果。它之所以有效，是因为它改变的是你和 Agent 之间对话的质量，而对话质量直接决定产出质量。它让我觉得最像在 XState 和顶级开发者一起工作的体验——感觉像一位水平极高的开发者在向我提出好问题。

**Q：你说过所有人都低估了你和 Agent 之间的沟通鸿沟？**
A：对，中间是有一道屏障的。你心里清楚自己的价值排序，就会以为 Agent 也能自然领会——总有那种"尽管相信模型就好"的感觉。但不管模型多聪明，它都不会读心术，不可能看穿你的心思，所以你必须有一套流程把你的价值观传达给它。很多时候你只定个目标、心想"随便给我刷一段代码"，产出的东西就会跟你完全脱节，因为它根本不懂你在意什么。Grill Me 不光是确立实现细节，它也是在划定范围：做这个、这个在范围之内、这个不在——这是 agent 了解你的过程。

**Q：什么是"聪明区"？盘问之后你还会介入吗，还是完全离开键盘？**
A：聪明区是 Dex Horthy 提的概念：你给 Agent 的上下文越多，每一个 token 都在大声争夺注意力，你往那个屋子里塞的声音越多，就越难听清真正重要的声音，模型于是开始丢掉事物之间的关联并因此犯错。上下文窗口里确实存在表现比较好和比较差的区域，就是聪明区与笨拙区。在目前的顶尖模型里，我认为大概是前 15 万个 token——不管窗口是 100 万还是更大，全看 token 的绝对数量。至于介入，我当时主要按"完全离开键盘"来设计：有个说法叫白班和夜班，跟 Agent 协作的最佳方式就是在白班做规划，到夜班让 Agent 干活，但愿早上醒来能看到写得清爽漂亮的代码。我一直在优化的是：踏踏实实做完一大块规划，让 Agent 跑上两三个小时，我好去干别的工作，再回来审查代码。

**Q：Wayfinder 解决的是什么问题？**
A：深挖会撞上线——比如"帮我做个 Stripe 克隆"，你绝不可能在 15 万 token 里把它全规划完。所以需要一个东西：它得完全清楚这次深挖的目的是什么、到目前为止决定了什么、眼下有哪些并行的深挖会话。这就是**地图**，你所有决策所需信息的核心集结点。有了地图，你会发现有些点像里程碑一样必须定下来，而且还有"战争迷雾"：每完成一次拷问环节地图上就解锁更多地点，路径像一张有向无环图。地图里每个环节就是一张工单，有拷问、调研、配置基础设施等不同类型；我的某些地图上有过 50 张甚至 100 张工单。我还一直用它规划课程，甚至用它设计自家花园里的花园办公室——工程也不过就是一门专业。

**Q：软件工程算不算"真正的工程"？为什么 Agent 特别擅长它？**
A：有位嘉宾采访过化学、机械、土木工程师，想弄明白软件工程到底算不算真正的工程，最后觉得可能确实算，但指出有一点截然不同：我们打交道的材料。其他领域里材料都有耐受极限，你只知道它大概能承受多大力；但在软件里材料本身就是软件——一段代码你运行一千次，它一千次做的事情都一样。不过现在有了大语言模型，我们也会遇到那种方差，说不定两边的方法可以互相借鉴。Agent 擅长的原因也在此：它的输入输出全是文本（代码、文档、指令 → 更多代码、测试套件、类型检查结果）；任何非文本的东西——比如悬停时动画不对劲——它给出的都跟垃圾一样。

**Q：你试过规格驱动开发，结果不理想？**
A：我对它算是有好有坏，而且这是个很奇怪的词，它涵盖的东西太多了。有个流行说法是"英语真的是最火的新编程语言"，我想着也许只要写一份规格说明、随时修改它、让 Agent 边做边改就行。但随着深入实验，每次我按"改规格→看代码变化"这种循环来跑，代码就会变得更烂，而且一点都没有变好。按说人是不该去看代码的，但我看了一眼，简直就是垃圾。我就想：Agent 在这种环境下怎么可能表现得好——反馈回路对 Agent 太关键了，测试套件很烂，它拿到的信号就很烂，跟人一模一样。

**Q：然后你怎么找到出路的？**
A：我翻开了书架上那本书，第一次抽出来的时候塑料膜好像都还没拆——《程序员修炼之道》。里面有一整节讲软件熵增：熵的意思就是"我总是倾向于走向更混乱的状态，这比走向有序的概率高得多"。我意识到软件熵增不可避免，而 Agent 制造熵增的速度比以前任何时候都快。那本书已经出版 25 年了，里面的概念却像为今天写的：不要超出车灯照射范围、永远在反馈回路内工作、巧合编程、曳光弹开发。这也带出我的核心判断：AI 跟人太不一样，你必须去适配它——想象你面对的是一个每天早上醒来都不记得自己是谁的人，就像《记忆碎片》的主角，这就是我戏称的"记忆碎片驱动开发"。我们是在为新人优化代码库，要努力做出有史以来最健康的代码库。

**Q：为什么几个术语就能改变 Agent 的行为？DDD 的通用语言又是怎么进来、效果如何的？**
A：我在 prompt 里开始用那些短语，然后注意到它也会用这些短语回敬我——"好的，我来把这个做成曳光弹开发，既然这是曳光弹开发，那我就这么做"。它在自己的推理链里用上了我说过的词。我把这类词叫**引导词**，或者用一个挺高大上的文学词汇：主导动机（leitmotif）。它们见效是因为 Agent 的先验知识里本来就有——这些书现在还在印，如果那些概念在训练数据里被串联过，引导词就能唤醒它们。这跟现实中跟专业人士沟通没多大区别：他说了一个恰当的词，同行立刻就懂了，这就是行话，它让事情变快、变简单、减少误解。至于 DDD，是因为 Agent 实在太啰嗦了（尤其 Opus 5），我想让双方开始用共同语言交流，于是找到了 Eric Evans 书里的**通用语言**，把 Grill Me 改成了 grill with docs——名字起得很烂，但本质就是构思应用时顺手建立领域语言。一旦用上，效果判若两人：突然之间你们在说同一种语言了，你能用少得多的字句描述你想改动的东西。比如我手头这个应用里有一种很复杂的交互——有草稿单元、草稿课程、草稿课，当你把某节草稿课变成正式课，意味着那个草稿单元和草稿课程也得转成正式，这要怎么解释？其实就是一个特定的级联术语（转录作"吉连实力化"，待核）。这些术语是我跟 Agent 一起想出来的，它其实非常擅长提炼术语；如果还能把它融进代码本身，那事情就成了，一个简单的 grep 就能找到提到那个术语的函数。

**Q：怎么向非工程团队的利益相关方证明投资基本功很重要？**
A：十年前你也可以问同样的问题，而且同样成立。我们以前会问"要不要还技术债"，其实是一回事。你需要某种指标，而现在要弄清楚稍微容易一点，因为 Agent 能让你跑得更快。第一步就是在你的组织里对每一个 Agent 建立可观测性：看它在做什么、成功率和失败率是多少——以前我们从来不可能对开发者这么做，那有点太冒犯了，但对 Agent 就应该这样，我们付了服务费，需要了解优化的效果到底怎么样。然后找个人（全职或部分工作）去读这些数据，找出哪些仓库成功率更高，把经验提炼出来分享给大家。组织还需要围绕一套通用的 skill 凝聚起来，一套通用的软件工作流，好做实验、做 A/B 测试；而定规则、决定在哪用在哪不用，必须百分之百由人类来做，甚至根本不让 AI 介入。

**Q：为什么你说"我正在放弃我的本地开发环境"？云端好在哪里？**
A：因为本地对我来说完全讲不通了，那感觉就像在浪费算力。光靠你和你的终端是不够的：现在每个开发者手头好像都有一百个终端，应该把这一百个终端提供给整个团队用，得能在共享空间里协作、能 at 一个人进你的盘问会话——所以把这些交互放到 Slack、Discord、Teams 或 Linear 很有意义。我坐火车来的路上就是在 Discord 里跟我的 Hetzner 机器聊天，给课程写东西、修学员的 bug；那台机器一直开着、能设定时任务，我还会跟自己的 Agent 开个类似晨会的东西让它安排一天的日程，它也能看懂我的 Discord 聊天记录。本地的痛点也很明显：上千个 Git 工作树堆在硬盘里，一个工作树要跑差不多五个 Docker 容器。据 Ramp、Stripe、Uber 这类公司的平台团队观察，70% 到 80% 的开发者是自愿转向云端的。

**Q：现在有种反向观点——Agent 实现太快，可以少做前期规划。你怎么看？怎么选？**
A：这取决于你在做什么样的工作，我觉得不该什么事都用 Grill Me。真正需要用 Grill Me 的，是那些实际要做、规模相当大、而且很难回退的工作，比如一个全新的页面或一个大功能——因为如果 Agent 写错了，错误的代码会留在它的上下文窗口里，影响之后的所有东西，事后再倒回去改、做对齐，成本会很高；这些情况就该先把所有棘手的问题（JSON、Cookie、认证 token 之类）回答清楚，然后再动手。判断方式很简单：这事小到可以事后再对齐？那就别用 Grill Me。一次会话能不能搞定？那就用 Grill Me。它跨了多次对话、需要对整件事对齐方向？那就用 Wayfinder。这跟以前写 PRD 的做法也很像：跨月的项目花一两天做规划不算坏事，一天的项目就别费这个劲了，一年的项目就该把它拆得更小。

**Q：有人会说这不就是瀑布模型吗？**
A：这个质疑反复出现。但 Agent 给了你一种直接批量倒垃圾代码的能力，有时候你可以把这点化为优势：做原型就是为了摸清它大概长什么样，你可以直接搭出三到四个不同版本，选你最喜欢的一个去迭代——以前做原型的成本向来很高，现在是史无前例的便宜，所以写规格说明书非常核心的一部分，就是去把这些原型做出来。另外 Grady Booch 说我们其实不该批评瀑布模型：亚马逊、微软、谷歌、Meta 这些大厂一直在做"微型瀑布"——先定计划、达成一致、动手做、发布上线，全都在两周到三个月里搞定。瀑布模型的问题从来不是规划本身，而是**动不动就按年来算**：规划做一年、实现又花三年，四年后做出来的根本不是我们想要的东西。整个行业已经有几十年没见过真正的瀑布模型了。所以哪种模式更契合 Agent？肯定是敏捷开发，因为人工成本降了这么多，我们随时可以极快地改代码。

**Q：TDD 在 Agent 时代还合适吗？技术债又该怎么办？**
A：我跟 Kent Beck 聊过，TDD 在很多方面可能都非常合适，但我还是没怎么看到有人真正这么用——大家在写测试、Agent 也是事后补测试。TDD 针对的是人类很小的工作记忆：先写一个理应通不过的测试，就算你分心去喝咖啡、散长步，回来时测试还挂着提醒你做到哪了。Agent 不需要这个，它们的"工作记忆"比人类大得多，真正需要的是反馈回路。所以哪怕我不用完整流程，我也经常对它说：证明你的改动确实做到了你声称做到的事，给我符合 TDD 精神的证据。另一半问题是 Agent 爱写同义反复测试——测试只是在断言实现细节本身，就像把实现代码抄了一遍。至于技术债，有人发推说"过去当代码库足够大的时候，技术债是你不得不忍受的东西，现在不在世了"，我回复：现在哪怕在极小的代码库里你也能忍受它了。因为 Agent 无法做战略性思考，只盯着眼下在做的事，极容易产出垃圾。对抗办法是自动化审查：一个实现 Agent 干活，另一个审查 Agent 推行编码规范、抓出同义反复测试，随时间提高测试套件质量。

**Q：你住在英国、离硅谷很远，这对做 AI 教学是变容易还是更难？教学行业变了吗？**
A：我其实就是在各走各的路。我挺早就意识到自己根本没能力预测未来——我离那些核心圈子太远了，只是身处一线在用这些东西的人，不知道模型会不会变强，也没有内部特权渠道。所以我只专注于眼下行得通的东西，这反而帮我收拢了一点关注范围，而且现在效果居然这么好，我自己都挺意外。如果我住在旧金山大概也能做这些事，但我可就得住在旧金山了，我可不想去那儿，我父母就住在同一条路上，我儿子也在乡下长大。至于教学行业：人们的学习方式其实没怎么变。"直接来个 Agent 就能把什么都教会你"这种想法听着很吸引人，在某些场景下确实管用，但**你真正想要的是内容编排**——你要的是一个真人参与进来，理解信息之间的脉络流向。我总觉得信息就像一张图谱：一个知识点依赖另一个，把这张图谱理成一条线性路径就是我对自我工作的定义，就像在图谱里跑一遍 Dijkstra 算法；这种程度的编排说到底又是战略层面的东西，而这不是 AI 特别擅长的事。

**Q：这算是你跟当年"从配音转向教课"一样的转型吗？你对刚入行的新人有什么建议？**
A：我觉得我基本上就是运气好，在对的时间选了对的事情。当初别人费了挺大劲才说服我转向 AI——大概两年前是我的合伙人一直催我"你真得试试这个"，我实际尝试了大概三个月，一次次试、一次次失败，最后才意识到这东西确实厉害。我尽量不把它编织成某种叙事，因为我也犯过好几个错误，也很容易就落到另一个领域里去——那也没什么不好，大不了回去接着做工程师。对新人，我现在其实很想像个新人一样重来一次，很怀念 2014 年给学生做工具的那种状态：正确的做法是尽可能多地使用这些 Agent，因为以后大家都会这么工作；关键在于保持好奇心、保持适应力。回想我当年那个频谱分析工具里撸出来的纯垃圾代码，如果当时有个 Agent 跟我一起做，效果肯定好得多——那时帧率掉到每秒十帧，如果我能这么说，它就会看到那六层嵌套循环，然后说"你这里也许该换个写法"。

**Q：有人把团队里那个默默清理坏习惯的人叫"园丁"，你怎么看？什么样的技能组合能造就优秀的软件工程师？**
A：我回复说：你的团队唯一需要的就是园丁——大概也确实需要其他几个人。我非常喜欢"杂草霸占花园、然后把它们清理出去"这个说法。我还发过一条推文说，我们本质上就是 Ralph 的平台工程团队——我们就是自己 Agent 的平台团队，在努力为它们搭建能取得成功的环境，这同样是战略层面的事。花园本身就很容易发生熵增，在这些东西变成问题之前理解并排查出它们，就是一项核心技能，甚至可能就是那项最核心的技能。要我用一个词概括优秀工程师的技能组合，我觉得会是**内省**——审视你自己，并且有能力把自己做的事提炼出来，变成 AI 能拿来干活的东西。就像在 Vercel 做 AI SDK 的 Lars Grammel（转录作"Last Grammar"），他正在给自己的开源库打造一整套"软件工厂"；我们又聊回管道工、聊回园丁，聊到思考软件开发的流程。最后推荐三本书：《程序员修炼之道》、John Ousterhout 的《软件设计哲学》，还有 Eric Evans 的 DDD——尤其读前三章，里面讲通用语言和领域建模的部分都非常棒。

## 三、备忘

**书籍**
- 《程序员修炼之道》（The Pragmatic Programmer）——Matt 说"几乎读到的每一行我都觉得简直是为今天写的"，出版已 25 年；关键概念：软件熵增、不要超出车灯照射范围（Don't outrun your headlights）、永远在反馈回路内工作、巧合编程（Programming by Coincidence）、曳光弹开发（Tracer Bullet Development）。转录中"适踪弹 / 失踪弹 / 适中谈开发 / 失踪但开发"均指曳光弹开发。
- 《软件设计哲学》（A Philosophy of Software Design，John Ousterhout）——深度模块（deep modules）；也提供了战术性编程 / 战略性编程的区分。主持人在节目末尾推荐了对 Ousterhout 的专访。
- 《领域驱动设计》（DDD，Eric Evans）——通用语言（Ubiquitous Language）、领域建模；Matt 反复强调"读前三章"。
- 《人月神话》（The Mythical Man-Month）——Matt 说"我手头已经有了，那是必须的"，距今 50 多年。

**概念 / 术语**
- 战术性编程 vs 战略性编程（tactical / strategic programming）
- 聪明区 / 笨拙区（smart zone / dumb zone，Dex Horthy 提出）——目前顶尖模型约前 15 万 token 表现最好，与窗口总大小无关
- 软件熵增（software entropy）
- 垂直切片 vs 水平切片（vertical slice）
- 曳光弹开发（tracer bullet）
- 引导词 / 主导动机（leitmotif）——在 prompt 或 skill 里重复某个精准短语来引导 Agent 行为
- 通用语言（Ubiquitous Language）、领域语言 / 行话
- 记忆碎片驱动开发（memento-driven development，Matt 戏称）——为"每次都从零开始、没有长期记忆"的 Agent 优化代码库
- 白班 / 夜班工作节奏（白天做规划，夜晚让 Agent 执行）
- 有限状态机、有向无环图（DAG）、战争迷雾（fog of war）、地图（map）
- 同义反复测试（tautological tests）——测试只是把实现代码抄一遍
- 幂等性 / 幂等键（转录作"密等性""加密等件"）、速率限制（转录作"评次限制"）、bearer token（转录作"bear token"）、JSON
- 可观测性（对每个 Agent 做可观测性：成功率、失败率）、自动化审查（automated review）
- 微型瀑布（mini-waterfall）——Grady Booch 观点：瀑布的问题在于动辄按年计，不在于规划本身
- 三峰薪酬模型（The Trimodal Nature of Software Engineering Salaries）——主持人 Gergely Orosz 的文章，转录作"Tray Model Nature of Software Engineering Compensation"
