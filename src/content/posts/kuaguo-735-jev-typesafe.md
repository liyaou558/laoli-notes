本期是「跨国串门儿计划」克隆的 Latent Space 2026-09-21 期「Why We Made Jev」，主持人 swyx 对话 TypeSafe 联合创始人兼 CEO Diogo Almeida。Diogo 曾在 OpenAI 参与 InstructGPT 与指令遵循方向的早期工作，如今他带着 Jev 回到公众视野，给出的却是一套对当下主流范式的系统性反问：Jev 被定义为「机器原生、系统 1、大型可编程模型」——它不是为了与人聊天，而是为了被代码直接消费，并在软件中承担大量细小、可验证的决策。整场对谈横跨模型训练、后训练方法、API 设计与软件产品，长度 128 分钟，信息密度很高。以下按核心观点、关键问答与备忘三部分整理。

## 一、核心观点

### 1. AI 的问题不是不够聪明，而是缺少正确接口
Diogo 抛出的第一个反常识判断是：今天的 AI 已经展现出远超预期的抽象与推理能力，但这些能力并没有通过合适的接口进入经济活动。他给出的著名疑问是，「我们怎么能去解数学里的千禧年大奖难题，却连最基础的工作都还自动化不了？」在他看来，问题的症结不在模型智商，而在于人机之间默认的接口形态——聊天框。Jev 的目标因此被定义为让代码而不是人，成为模型的直接使用者。它承担的不是「陪你对话」，而是软件里大量细小、可验证的决策，被程序调用、被程序校验、被程序复用。

### 2. RLCD 是面向程序化使用的新北极星
Diogo 把 TypeSafe 的方法论浓缩为一个新命名——RLCD。他认为 RLHF 的核心是指令遵循，RLVR 的核心容易滑向刷基准，而 RLCD 关注的是模型在程序化使用中的可靠性。重点不在某个具体算法，而在于为模型选择正确的任务和方向。他在节目里直言：「对我们来说，RLCD 就是这个新任务，我不觉得它是行业黑话。」这个判断背后的立场是：与其在已有评测上争夺小数点，不如重新定义模型应该被训练去做什么。

### 3. 数据和任务比算力更重要，TypeSafe 是「数据实验室」
TypeSafe 更愿意把自己称为数据实验室，而不是模型实验室。Diogo 认为，真正困难的不是单纯扩大模型规模，而是找到正确的任务、构造与任务匹配的数据，并持续修复模型能力参差的部分。他给出的排序相当明确：「显然数据远比算力重要，而选对任务、确立北极星目标，才是最难、最重要的事。」这也解释了他为何反对把「花十亿美元预训练」当作必然路径——钱能买到算力，买不到正确的任务定义和干净的数据。

### 4. API 里的拒绝响应可能是一个类型错误
面向聊天产品的安全对齐，可以让模型拒绝用户不应提出的请求；但当模型作为软件依赖运行时，随机拒绝会让整个系统变得不可预测。Diogo 区分了安全对齐（safe alignment）与能力对齐（capability alignment），强调 API 更需要按用户意图稳定执行。他的原话很锋利：「而且拒绝响应明显就像是一个类型错误。」换句话说，当一段代码调用模型并期待一个可解析的结果，却收到一句「抱歉，我不能帮你」，这在工程上等价于类型不匹配——调用方没有处理分支，系统就会崩。

### 5. 可靠性不等于确定性，鲁棒性才是软件真正需要的特性
Diogo 拆解了一组常被混淆的概念：相同输入是否始终得到相同输出，只是确定性问题；而真正适合软件的目标，是相似输入得到相似结果，并且模型在不同表达、随机数和上下文变化下保持鲁棒。他坦言：「我认为鲁棒性才是大家……更重要的特性。」对软件工程而言，模型不可能完全确定性，但可以要求它在扰动下不出现行为突变——这才是能写进测试用例、能设置阈值的性质。

### 6. 把 AI 工作流拆成最小语义单元，让它可评测
与其用一个巨大的系统消息要求模型一次性完成所有事情，Diogo 主张把任务拆成许多独立、明确、可评测的决策。这样每个行为都能通过代码验证、设置阈值，并沉淀为测试用例。他反复强调自己的偏好：「我喜欢把东西拆成最小的语义单元。」这与他对可靠性、鲁棒性的要求互为因果——只有把决策颗粒度切到足够小，才能对每个单元独立判定成功与否，才能把「模型表现如何」从玄学变成可度量的工程指标。

### 7. 结构化状态将取代巨型系统消息
Diogo 指出，软件内部真实存在的是状态、变量、指令和嵌套结构，而不是一串扁平字符串。把所有内容塞进系统消息，类似使用难以维护的全局变量；机器原生模型应当直接处理结构化 JSON 和程序状态。他的比喻相当生动：「系统消息就像恶心的全局变量，你把什么东西都往里塞，把所有指令一股脑全放进去。」这既是一个 API 设计主张，也是他对「机器原生模型」这一概念最具体的解释——模型要理解的是程序的状态机，而不是人类的自然语言长文。

### 8. AI 最终应该隐入软件背景
在 Diogo 描绘的未来里，AI 不必一直以聊天框或「AI 同事」的形式出现。它会成为软件底层的通用基础设施，嵌入已有产品，自动化那些今天仍由人手工完成、但用户甚至无法想象如何自动化的工作。他称之为「SaaS 反向末日」式的前景——不是 AI 取代 SaaS，而是已有软件因获得模型能力而扩展。他的收束句是：「我觉得这个世界应该让人感觉更惬意，而 AI 只要在背后帮着实现这一点就好。」真正的经济变革，不是让 AI 充当主角，而是让软件获得此前无法实现的自动化能力。

## 二、关键问答

**Q1：Jev 到底是什么？它和主流大模型有什么本质区别？**
A：Diogo 把 Jev 定义为「机器原生、系统 1、大型可编程模型」。它不是为聊天而生，而是为被代码直接消费而生，在软件中承担大量细小、可验证的决策。「系统 1」意味着它偏向快速直觉式的响应而非长链条深思，契合程序调用对延迟和稳定性的要求。它的使用者是程序，不是人。

**Q2：为什么叫「机器原生」？**
A：因为它的输入输出形态从一开始就按机器的需要设计——直接处理结构化 JSON 和程序状态，而不是把一切都压成自然语言字符串。Diogo 认为软件内部真实存在的是状态、变量、指令和嵌套结构，机器原生模型应该理解这些，而不是被要求去解析一段巨大的、类似全局变量堆砌的系统消息。

**Q3：为什么把 RLCD 当作新北极星，而不是继续做 RLHF 或 RLVR？**
A：Diogo 认为 RLHF 的核心是指令遵循，RLVR 的核心容易滑向刷基准，两者都没有直接针对「程序化使用中的可靠性」。RLCD 关注的正是后者。他强调重点不在具体算法，而在为模型选定正确的任务和方向：「对我们来说，RLCD 就是这个新任务，我不觉得它是行业黑话。」

**Q4：他为什么说 RLHF 会带来模式丢失、校准失真与智能碎裂？**
A：在 Diogo 看来，用人类偏好做后训练，会把模型原本丰富的能力压扁成符合偏好的少数模式，导致模式丢失；模型对自己的置信度也会失真，即校准不良；同时能力被切碎，出现「会解千禧年难题却做不好基础工作」的参差。这正是他要跳出 RLHF 框架的原因。

**Q5：为什么拒绝响应在 API 语境下是「类型错误」？**
A：面向聊天产品的安全对齐允许模型拒绝用户请求；但当模型作为软件依赖被调用时，随机拒绝会让整个系统不可预测。Diogo 区分了安全对齐与能力对齐，主张 API 应按用户意图稳定执行。调用方期待一个可解析结果却收到拒绝，在工程上就是类型不匹配——「而且拒绝响应明显就像是一个类型错误。」

**Q6：可靠性、鲁棒性、确定性，这三者有什么不同？**
A：Diogo 把三者明确切开：相同输入始终得到相同输出，只是确定性问题；而软件真正需要的是相似输入得到相似结果，并且模型在不同表达、随机数和上下文变化下保持鲁棒。他说「我认为鲁棒性才是大家……更重要的特性」——因为绝对确定性在生成式模型上不可能实现，但鲁棒的行为边界可以被测试和约束。

**Q7：怎么让 AI 工作流变得可度量、可测试？**
A：做法是把任务拆成许多独立、明确、可评测的决策，即「最小的语义单元」。每个单元的每个行为都能用代码验证、设置阈值，并沉淀为测试用例。Diogo 说：「我喜欢把东西拆成最小的语义单元。」这样「模型表现好不好」就从主观感受变成可跟踪的工程指标。

**Q8：为什么巨型系统消息是个坏设计？**
A：Diogo 的比喻是：系统消息就像恶心的全局变量，你把什么东西都往里塞，把所有指令一股脑全放进去。这导致难以维护、难以定位失败。他主张用结构化状态来取代它——让模型直接处理 JSON 和程序状态，而不是让模型去猜一坨越长越乱的字符串到底想表达什么。

**Q9：为什么拒绝公开评测榜？**
A：节目中专门有一节讨论「为何拒绝公开评测」。结合他的整体立场，Diogo 认为公开基准容易被 RLVR 式地刷分，排名的意义有限；相比之下，可靠性、鲁棒性和「单位美元智力比」才是客户真正在意的指标，也是 TypeSafe 愿意为之负责的目标。

**Q10：《最苦涩的教训》对这个团队意味着什么？**
A：节目在以「《最苦涩的教训》与数据」为题的段落中讨论了这个话题。Diogo 的立场是：算力与通用方法确实重要，但这不意味着放弃对任务和数据的选择——他明确说「显然数据远比算力重要，而选对任务、确立北极星目标，才是最难、最重要的事」。TypeSafe 因此自称数据实验室。

**Q11：为什么强大 AI 至今没有自动化多少经济工作？**
A：这是 Diogo 长期追问的核心问题——为什么 AI 能解千禧年大奖难题，却仍无法稳定自动化大量基础、机械、具有经济价值的工作。他的回答指向接口与任务定义：能力没有通过合适的接口进入经济活动，也没有被拆成可验证的最小决策单元，所以停留在「很聪明但用不上」的状态。

**Q12：为什么不花十亿美元去预训练一个大模型？**
A：节目专设「为何不花十亿美元预训练」一节。Diogo 的逻辑是：钱能买到算力，但在任务选择、数据构造和能力缝隙修复上并没有捷径；真正的瓶颈不是规模，而是找对方向和构造匹配数据。这也是他宁愿把 TypeSafe 称作数据实验室、并把资源投向 RLCD 与程序化可靠性的原因。

**Q13：什么是「SaaS 反向末日」？AI 会取代软件吗？**
A：Diogo 描绘的恰恰是反面：不是 AI 取代 SaaS，而是已有软件因获得模型能力而扩展，他把这种前景称为「SaaS 反向末日」。AI 会作为底层通用基础设施嵌入已有产品，去自动化那些今天仍由人手工完成、用户甚至无法想象如何自动化的工作。

**Q14：Jev 在电脑操作和编程 Agent 上打算怎么做？**
A：节目后半段覆盖了「电脑操作与主要用例」「Jev 重塑编程 Agent」，还延伸到暗数据、实时场景与多 Agent 未来。Diogo 的思路一以贯之：把编程与操作类任务拆成最小语义单元，用结构化状态和程序在环反馈来保证可靠性，让模型成为编程 Agent 里可被验证的执行部件，而不是一个随时可能「跑偏」的聊天对手。

**Q15：他从 OpenAI 的经历里带走了什么，又否决了什么？**
A：Diogo 参与过 InstructGPT 与指令遵循方向的早期工作，熟悉前沿模型训练与后训练。节目还专门谈到「TypeSafe 背后的 OpenAI 故事」与「多数 NeoLab 为何做错 AI」。他带走的是一线训练经验，否决的是把聊天机器人、公开刷榜和「AI 同事」当作默认范式的惯性——最终走向机器原生、程序在环、以可靠性和数据为核心的路线。
