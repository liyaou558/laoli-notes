## 一、核心观点

### 1. AI 还替你分不了 bug 的诊
Mario 说，从 2025 年 2 月到大约 7 月，他每天大部分时间都花在维护 Pi 上——看大家报的问题、修问题。Pi Durable 早就做出来了，但 Agent 还没法真正帮上这些忙。他说自己还没那么信任它们，没法把"判断哪些 issue 值得我们花时间、哪些不需要修"这件事交出去。所以至少他仍得把所有提交的问题过一遍，分诊、挑出真正值得投入的。Agent 能修问题（"能，当然能"），问题只是"他修得好吗"：小问题可以放心交给 Agent，一旦涉及设计或架构，还是得有人来。

### 2. Agent 修 bug 几乎不可能不增加代码
Armin 指出一个很怪的现象：Agent 肯定能解决问题，但几乎不可能在不加代码的情况下把问题修好——而很多问题修完之后，代码库的代码量其实不应该净增加。主持人当场吐槽"这话居然是那个老发带着 205 处改动的 PR 的人说的"，Armin 自嘲"我知道，太吓人了，我自己用铁皮机器人也把自己坑了"。他真正担心的是：如果代码库完全靠自动化来维护，"每修一个 bug，代码量自然就会涨一点"，时间一长就堆成一坨只完成了一部分的代码。

### 3. 性能问题：Agent 擅长找、不擅长根治
Mario 以 Pi 的终端界面库为例：最初的设计是他 2025 年初为另一个项目手写的，很稳健、很精简。后来做 Pi 时，他直接对 Agent 说"API 在这，就照着这个 API 写，把这些组件都给我做出来"，markdown、文本、编辑器组件"我一行都没看过，我根本不在乎"，只要能用、再有一套测试保证渲染正确就行。只有性能下降时他才会在意——而这时 Agent"通常很擅长找出一堆问题，但很不擅长想出一个通用的解决方案"，只会做局部修补让某个边界情况变快，不会从整体去找出架构上的病根。这正是他觉得自己"多少还值点钱"的地方。

### 4. 有明确判定标准的任务，Agent 表现惊人
只要任务结果很明确、只有完成和没完成两种情况，Agent 的能力就会大幅提升。案例：① 逆向 Java 虚拟机内部的原生数据结构——整套防护很严密、原生代码那边只留了一个"任何人都不可能发现并利用"的突破口，AI 却直接去逆向 JVM 内部结构、读进程内存，再对应到正确的 JVM 构建版本；② 约 500 美元逆向一个国产 CarPlay 适配器（USB 芯片），AI 自己搞懂了解密、还在网页界面找到一个可绕过限制的 CGI 文件，"整个东西就归我掌控了"；③ 从零写一个任天堂 DS 模拟器并成功跑起来（DeepSeek 做的）。结论就是："如果你有一个能告诉 LM 他做得对不对的判断依据，你基本上就赢了。"

### 5. 模糊测试像给测试加火箭燃料
Armin 拿一堆实例文件（INI、TOML、MessagePack、JSON 等格式）让模型实现一个序列化库，然后"往死里做模糊测试"，找出了很多问题。以前给库做 fuzzing 本来不算太难，但现在"真是不用想就能做"——修到"你得花上几个小时才能再找出一个回归问题为止"。再加上一个 LM，它还能推想出模糊测试生成器没有覆盖到的额外用例。"这就像给各种测试加上了火箭燃料，特别惊艳、特别实用。"他还提到 Bun 有一大堆测试，Jarred 让一群 Agent 用这套测试去驱动 Rust 重写，效果非常好。

### 6. 架构：不是能力问题，是训练数据问题
Armin 认为模型能完成复杂任务却做不好软件架构，根因在训练数据：网络安全、做网站、做前端、做"已经存在又有参照能判定对错"的东西，数据都很容易准备；但"设计一个东西、给它搭架构的这个过程，我没有训练数据"。在编程里，搭架构的过程是唯一通常不会以文字形式被记录、让 LM 无从学习的部分，"这就是我们卡在这里的原因"。Mario 补充：新模型自主权更大，所以架构结果反而更差；他还觉得模型"说话的方式"越来越怪、技术术语堆砌，宁可换回还在用的版本。两人都拿 DHH 那句"如果你觉得自己会做架构就很特别，那你得再想想"来对照——但模型真能把架构也拿下吗？至少在"最可能走的那条路径"上，模型的权重通向了别的地方。

### 7. Pi Durable：副作用三明治 + 幂等性
Mario 用五句话讲清持久性："Agent 在一个进程里启动；Agent 调用工具；然后进程挂了；你想要的是重启进程后，Agent 能从刚才停下的地方接着运行。"核心设计是"副作用三明治"：① 执行前先把执行意图写进存储（记录参数/输入，确认输入已正确求值）；② 执行副作用；③ 把结果持久化。不管进程在三明治的哪个环节崩溃，你都想得到那个结果。如果副作用发生在外部系统（比如给 GitHub Actions 发了一个请求、中途崩溃、你还不知道它执行了没有），就靠幂等性恢复：先安排一次运行拿到一个 ID 存下来，再真正启动；如果已经在运行，外部系统会告诉你并等你拿结果。信用卡扣款、删文件这类不可逆操作，则需要另行决定怎么配合这套持久性系统。

### 8. 应用状态：带版本的文档存储
除了"任务"（每个任务就是一个副作用三明治），Pi Durable 的另一块基础是应用状态——一个很小的文档存储（类似 MongoDB，存 JSON 对象），特殊之处在于能把某份文档的值关联到会话记录里的任意位置。这样回退时"你想要的是那个时间点对应的版本，还是不管走到哪都想要文档的最新版本"，两种都能表达。例如一块画布文档只存一串笔画，重放就能重绘画作；你一边和 Agent 聊一边在画布上画，文档就跟着会话演进而更新。存的是版本之间的差异（参考 JSON patch 规范，但针对 Agent 操作做了优化），实现上用了 Proxy 对象——"是个取巧、还挺慢的办法"，但对运行框架里要做的事很好用。Armin 意外于自己做了约 20 年网页开发，状态与不可变数据这类局部更新问题始终没有公认标准：Immer 大体做对了，Ink & Switch 的 Automerge 想用代理对象记录修改、背后生成无冲突的复制数据结构，但映射到 JavaScript 上"太多漏洞"。

### 9. 为什么做通用基础构件，以及"个人 Agent"的安全与上手
Armin 说，现成方案（Hermes、OpenClaw、各类 claw、Amp 的 Orbs）都得各自解决持久运行，但都不是通用方案，没法拿来就构建下一个项目、下一个开源产品，或公司内部的 Agent 系统。Pi Durable 想做的是一个很小的通用基础构件（大约 12000 行代码），开箱就能基本满足你对 Agent 的所有需求，包括上下文压缩等。Mario 泼冷水："你显然不需要它，你肯定不需要 Pi Durable，你完全可以自己做"——难的不是最后写了多少行代码，而是核心设计得让这套东西真能可靠运转、出错能恢复、没人盯着也能继续。Earendil 大致分两块：做产品（长远希望连非工程师也用得开心，"不希望明年还是一家做编程 agent 的公司"）和做基础设施组件。谈到个人 Agent，两人都说风险极高（"几百万人在把各种账号都登录到那台机器上，这就是一场灾难"），推广最大的难题是安全与"让新人上手"——"大家都只是在侧边栏给你放个聊天框，然后说祝你好运，自己搞明白吧"。

## 二、关键问答

Q: Armin，先自我介绍一下，你什么时候加入的？
A: Armin Ronacher，Earendil 的联合创始人（转写作"McPill"，应为 co-founder），自称"常驻实习生"。他和朋友 Colin 一起创办了这家公司，大约 2026 年 2 月把 Pi 纳入了公司。此前他们已花很长时间想拉 Mario 入伙，OpenClaw 那波"疯狂的热潮"之后机会来了，Mario 开始愿意考虑，因为他们想跟 Mario 合作、也想做"有价值的软件"，而 Pi 是这方面很棒的早期尝试。

Q: Mario 怎么看自己"被 Pi 套住了"？
A: 他自嘲"我做 Pi 真是个傻子，现在又跟 Armin 绑在一起了"。他做开源的历史很长，只要自己做的项目有人用，就会一直替大家维护这些"破玩意儿"，"哪怕他们一分钱都不给我"，负面声音有时也确实让人烦。目标是把 Pi 交出去——不是不做了，而是让更多人一起做、降低对他一个人的依赖，"不用非得我在才行"。他说这个目标实现得挺好，"就算我明天死了，Pi 也会有人好好接着做"。他搬来波兰时一个朋友都没有就办了线下聚会，如今它已是 meetup.com 上全国最大的聚会，自己就能运转，他"过去参加就行"。

Q: 用 AI 找贡献者的体验怎么样？你以前不太喜欢随便让 AI 呼出点东西来。
A: Mario 直言"很差"。2025 年 2 月到 7 月他大部分时间都在维护 Pi，看 issue、修问题。他还没那么信任 Agent，没法让它判断"哪些报的问题值得我们花时间"。Agent 能修问题，但关键问的是"修得好吗"：小问题可以放心交出去，涉及设计或架构就得有人来，否则 Agent 只会"在你代码库的某个局部拉一坨屎，把事情搞得更糟"。

Q: Armin 眼里 Agent 修 bug 的根本毛病是什么？
A: 它能解决问题，但几乎不可能在不加代码的情况下把问题修好；而很多问题修完以后代码量其实不应该净增。被吐槽"205 处改动的 PR"时他自嘲"我自己用铁皮机器人也把自己坑了"。他还说自己已经接受了一整套"AI 胡活"的工作方式："从某种角度来说，我觉得自己确实比以前笨多了，但换个角度，这样效率很高。"关键在于你在应用的哪一层让人参与、在哪一层放心让 Agent 产出能用的东西。

Q: 什么条件下 Agent 表现最好？
A: 当任务结果很明确、只有完成和没完成两种情况时，能力就大幅提升，"最后总能把它做完"。有能告诉 LM 他做得对不对的判断依据，"你基本上就赢了"。Bun 有一大堆测试（未必 100% 覆盖，但已经够用），Jarred 让一群 Agent 按测试去移植/用 Rust 重写，效果非常好。有参照、训练数据里又有相关信息的任务都容易测，也很适合做模糊测试。

Q: AI 逆向工程到底有多强？给两个例子。
A: Mario 见过 AI 逆向 Java 虚拟机内部的原生数据结构、直接读进程内存并对应到正确的 JVM 构建版本——"全世界没有哪个做逆向工程的人能做到那个程度，尤其不可能在那么短的时间里做到"。另一位嘉宾（主持人）的国产 CarPlay 适配器 USB 芯片，AI 自己搞懂了解密、还在网页界面找到一个可绕过限制的 CGI 文件，花了约 500 美元"整个东西就归我掌控了"。Mario 家里堆了很多硬件，从最小的本地模型一直到 DeepSeek 和 GLM 都在跑这类实验，还让 DeepSeek 从零写了任天堂 DS 模拟器并跑起来。

Q: 模糊测试 + LM 的组合好在哪？
A: 让模型实现序列化库后交给 fuzz 往死里跑，找出很多问题；再修到"要花上几个小时才能再找出一个回归问题"为止。LM 还能推想模糊测试生成器没覆盖到的额外用例，"这就像给各种测试加上了火箭燃料"。Armin 觉得凡是能做模糊测试的东西都差不多，特别惊艳、特别实用。

Q: 为什么模型能力很强，架构却上不去？
A: 训练数据说了算。有参照能判定对错、已经存在的东西（网络安全、网站、前端）数据都好准备；但"给一个东西搭架构的这个过程"在编程里是唯一通常不会以文字形式被记录、让 LM 无从学习的部分，所以卡住。Mario 补充：新模型自主权更大，架构结果反而更差。也可以把它看成一个分类问题——如何从海量交互记录里挑出真正高产出的对话（比如 Pi Durable 经过好几轮迭代，训练时怎么确定哪次对话最终产生了发布版本），这要难得多、样本也少得多。

Q: Pi Durable 的"持久性"到底指什么？
A: 五句话：Agent 在进程里启动 → 调用工具 → 进程挂了 → 重启后能从刚才停下的地方接着运行。你要的不是输入"继续"，而是工具结果与助手的流式输出都不丢、应用状态能可靠持久化并能可靠恢复。长时间运行的 Agent（各种 claw）都需要它；它还顺带解决了"把整颗会话都加载进内存"的问题——比如一个在 Slack 里待上好多年的机器人，完整历史有海量消息，不能全发给 LM，但你又得保留全部历史。

Q: 那你们用事件溯源吗？
A: 主持人猜是"提交到文件 + 事件队列"。Mario 证实"这恰好是我们没做的事——我们不用事件溯源，其他人都在这么做，我们不这么做，因为它有很多问题"。他们改用前面讲的"副作用三明治"：先存执行意图、再执行、最后存结果。

Q: 崩溃可能在哪些时刻发生，分别怎么恢复？
A: 三个阶段：执行前崩溃——意图已保存，重启后查存储发现有待执行操作，直接执行；执行中崩溃——若副作用在外部系统，就靠幂等性（先安排一次运行拿 ID 存下来，再真正启动；已在运行就等结果）恢复；执行后崩溃——结果已经持久化，拿到结果即可丢掉其余过程信息（除非要留日志/审计）。不可逆的副作用（扣信用卡、删磁盘文件）则要另行决定怎么配合。

Q: 应用状态怎么存？版本怎么处理？
A: 一个很小的文档存储，可把文档关联到会话记录的任意位置，回退时可选"当时那个版本"或"最新版本"两种语义。画布文档只存一串笔画，重放即可重画。存的是版本之间的差异（参考 JSON patch、针对 Agent 操作做了优化），实现上用了 Proxy 对象，是个"取巧、还挺慢"但好用的办法。Armin 对"做了 20 年网页开发、局部更新的状态问题始终没有公认标准"感到意外。

Q: 为什么决定解决持久运行，而不是框架里的其他问题？
A: 现成方案（Hermes、OpenClaw、各种 claw、Amp 的 Orbs）都不是通用方案，很难拿来构建下一个项目/开源产品，或公司内部的一群 Agent 系统。Pi Durable 想做很小（约 12000 行）却足够通用、足够强大的基础构件，开箱基本满足全部需求（含上下文压缩）。Mario 泼冷水："你完全不需要 Pi Durable，你完全可以自己做"——难的是核心设计能可靠运转、出错能恢复、没人盯着也行；编排 Agent 的那一层应该让人多少能理解、有点章法。

Q: 多人和多机协作怎么看？
A: Mario 说没见到好用的多人协作运行框架，生态又很碎片化、每天都有新模型新东西。他正在试着用 Hermes 带老婆一起协作，好少出点问题。他还让模型做了个"Parsels"（用 Pi 做的，把存会话的 JSON 文件从一台机器复制到另一台然后直接重启，因为所有环境变量都已经在里面）。长期方向是让"能自我修改的 Agent 软件"这条路走得通，从"我和一个铁皮家伙"变成"多台机器上的一堆家伙跟很多人交流"，能随时切换、把 Agent 和人按任意组合重新连接。

Q: 你们怎么看别的 Agent 框架？
A: 平时不太看别人在做什么——容易分散注意力，也分不清人家是在真的解决问题，还是"因为写代码不要钱"只做了个实验。Amp 比 Pi 早，团队对软件工程的未来有自己的设想、愿意押上房子赌一把，Orbs 好用、团队也懂行；OpenCode 也在跟持久化问题较劲；Claude Code 的 agent 框架变好了一点、更稳，但仍有 bug（莫名报错、不同会话内容串到一起）；DeepSeek 的 Agent 框架源代码读过，插件架构很聪明（"承诺的比能做到的多，但思路特别聪明"）。Armin 特别讨厌"请求用户补充信息"这个功能，也抗拒网页界面；他喜欢 DeepSeek 那种"像桌面应用里的 Pi"、可以放 Tailnet 从手机访问的形态。

Q: 安全、易上手，以及你们接下来对什么感到兴奋？
A: 网页插件系统/多人共享空间的安全很难：只要有人连上别人的会话就必须完全信任他，而铁皮家伙弄出的界面里可能直接就是跨站脚本攻击、能偷走 cookie，"一旦保证安全，体验就变得很烂"。Mario 前几天发现一个 agent 想把文件分享给另一台设备，结果把整个文件系统都暴露到公网约一天。Earendil 分产品与基础设施两块，长远希望连非工程师也用得开心、不想只做编程 agent。Mario 最期待"让新人上手"——"如果我能让我老婆、孩子都用上 Agent，好多事情就不再是问题了"，并吐槽"大家都只是在侧边栏放个聊天框，说祝你好运"。Armin 希望炒作消停一点、把技术用在很酷的地方做出更好的软件（而不是粗制滥造的 Photoshop 分支版本），并乐见 AI 已解决在电脑上模拟 PS5 的问题——"这甚至算是对社会的贡献，有助于把 PS5 游戏保存下来留给未来"。
