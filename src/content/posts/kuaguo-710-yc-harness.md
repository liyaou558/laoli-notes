## 一、核心观点

### Harness 不是包装层，而是能力本身
讨论以「harness 为何值得研究」开场。关键证据是 ARC-AGI 的结果：模型权重完全相同、运行框架不同，能力却可能出现数量级的差异。决定 Agent 能否用工具、能否管住上下文、能否获得反馈、能否适应新问题的，恰恰就是这个「被认为不配当科研课题、只配叫包装层和脚手架」的 harness。正如原话：「光靠一些 harness，我们就能做到 95%，而英伟达的 AVO 甚至做到了 100%。」——所谓 wrapper 的外壳，恰恰是能力的真正落点。

### 模型之外，才是「测试时经验」的入口
模型本身能力有限，ICL（in-context learning）会很快触及上下文饱和。真正让 Agent 持续适应而不必重训的办法，是 harness 把「测试时的经验」组织成记忆、工具、REPL、子 Agent 和反馈循环——让模型在一次又一次的执行中不断获得并沉淀经验。换句话说，进化与适应的主战场发生在模型参数之外的那层运行框架里。

### 好的 harness 应尽可能有表达力
不该把 Agent 框死在固定的「规划—行动—评估」流水线里。Seth 认为模型本身能够自行探索，harness 的职责是提供 compaction、Python REPL、子 Agent、状态与反馈这类能力，把选择和探索的自由交给模型自己。「你会希望它是你能想象到的最具表达力的东西。」框架越有表达力，Agent 越能自主演化出高效的做事方式。

### 上下文可以像缓存一样分层管理
用 L1/L2/L3 缓存的比喻理解上下文管理：不是一股脑全塞给模型，而是通过 compaction（压缩摘要）、程序化操作、子 Agent 等方式，减少重复生成、降低无效 token 消耗。把最相关、最常访问的信息放得越「近」，Agent 的主上下文越干净，长任务的持续能力越强。

### 自我改进的对象不只是 Prompt，还包括 harness 本身
进化链条可以一路延伸：从 DSPy 对系统提示词的优化，到达尔文—哥德尔机直接改 harness 代码，再到 continual harness 调整历史轨迹、技能、记忆与子 Agent 规范。「你不仅能改 system prompt，还能改 harness 本身——也就是正在跑的 harness 代码。」这意味着 Agent 的持续进化可以从提示层面一路下探到框架代码层。

### 长期任务的公平比较，必须纳入预算约束
要公平比较多个 Agent 在长期任务上的表现，必须把「预算」算进去。一个 Agent 预算耗尽停止了、另一个还在跑，两者的结果根本不能直接对比。任何脱离运行成本与资源上限的 Agent 评测，都会得到失真甚至误导性的结论。

### OpenJarvis 把「端侧运行」作为完整设计，而非只看本地模型
OpenJarvis 不只纠结于跑哪款本地模型，而是把模型、推理引擎、Agent 逻辑、工具、记忆、学习纳入五层原语统一设计。云端大模型负责「优化配置」，实际推理则在本地产物上运行，以改善成本、延迟、隐私与个性化。「经过 Claude 或 ChatGPT 这类云端大语言模型优化的 OpenJarvis 配置，效果远好于直接开箱即用的本地技术栈。」端侧 AI 的竞争力来自「云优化＋本地运行」的协作，而非单点模型性能。

### 沙盒的角色在转变：从 Agent 的「家」变成按需调用的资源
QM 把沙盒从 Agent 长住的「家」，改造成 Agent 按需调用的资源。当 Agent 不再被圈养在一处、自由度变高时，权限控制与「社交语境」判断就愈发核心——Agent 越自由，越需要清醒地把控它该被授予什么、放在什么语境里使用。

## 二、关键问答

**Q：为什么 ARC-AGI 的结果能说明 harness 很重要？**
A：因为测试里模型权重是相同的，唯一变量就是运行它们的框架。结果能力出现数量级差异，说明能力差异并不来自模型本身，而是来自 harness 决定的那一层——能否用工具、能否管上下文、能否获得反馈、能否适应新问题。所以 harness 不是可有可无的包装，而是把相同模型推上不同能力台阶的关键变量。

**Q：模型自身能力既然在快速变强，harness 还需要吗？**
A：需要，而且越来越需要。因为模型的 ICL 很快会触及上下文饱和——塞再多示例进去也会溢出。真正让 Agent 持续适应新任务而不必重训的办法，是把「测试时经验」沉淀进 harness 组织的记忆、工具、REPL、子 Agent 与反馈循环里。模型负责生成，harness 负责让经验可复用、可持续。

**Q：好的 harness 应该长什么样？**
A：应该尽可能有表达力，而不是把 Agent 锁死在「规划—行动—评估」这种固定流程里。Seth 的观点是模型能自己探索，所以 harness 要给足 compaction、Python REPL、子 Agent、状态与反馈能力，把探索与试错的自由交给模型。理想 harness 是「你能想象到的最具表达力的东西」。

**Q：上下文越长越好吗？怎么管理上下文？**
A：不是越长越好，要像缓存一样分层管理（L1/L2/L3）。通过 compaction 把长历史压成摘要、用程序化操作替代重复的文字推理、用子 Agent 把局部任务隔离出去，从而减少无效 token 与重复生成。把最常用信息放得越「近」，主上下文越干净，越能支撑长任务的持续运行。

**Q：Agent 的自我改进，具体改哪些东西？**
A：远不止 system prompt。可以逐层下探：DSPy 优化系统提示词→达尔文—哥德尔机改 harness 代码→continual harness 调整历史轨迹、技能、记忆与子 Agent 规范。最高层的自由是「你不仅能改 system prompt，还能改正在跑的 harness 代码本身」，让进化发生在框架代码层而不是只停留在提示层。

**Q：评测两个长任务的 Agent，怎么比才算公平？**
A：必须把预算算进去。一个 Agent 预算耗尽停下、另一个还能继续跑，两者的输出直接比较是不公平的。评测必须明确运行成本与资源上限，在同等预算约束下比较，否则得出的胜负结论是失真的。

**Q：OpenJarvis 和常见的「端侧模型」思路有什么不同？**
A：常见思路只纠结于本地跑哪款模型；OpenJarvis 把模型、推理引擎、Agent 逻辑、工具、记忆与学习纳入统一的五层原语设计，并引入「云端模型优化、本地实际推理」的分工。经过 Claude 或 ChatGPT 这类云端模型优化的本地配置，效果远好于开箱即用的本地技术栈——在改善成本、延迟、隐私的同时保住了个性化。

**Q：QM 对沙盒的设计做了哪些改变？**
A：把沙盒从「Agent 长住的家」改成了「按需调用的资源」，让 Agent 不再被固定圈养在一处。代价是 Agent 自由度更高，于是权限控制与社交语境的判断变得更核心——越自由的 Agent，越需要严格管控它被授予的权限和使用语境。

**Q：这期讨论对普通做 Agent 的人有什么启示？**
A：别再只盯着换更强的模型、调更好的 prompt。真正拉开能力差距的，往往是那层「不起眼」的 harness——上下文怎么管、经验怎么沉淀、工具怎么接、子 Agent 怎么派、自我改进落在哪一层。把框架做「活」、做有表达力，比单纯堆模型参数更能提升 Agent 的长期真实能力。
