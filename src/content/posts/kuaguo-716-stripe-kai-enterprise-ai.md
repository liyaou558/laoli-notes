## 一、核心观点

### 1. 企业 AI 的真问题不是「提供 AI」，而是「提供治理结构」

Sharadh 说得很直接：2026 年初海量 AI 工具迎面铺来，Claude Code 刚席卷全球，他和同事最开始的困惑是「怎么让每个人都用上 AI」。但他们很快意识到，这绝不只是工程或技术问题，更难的是「如何在大规模下复刻一家公司的运作方式」。Stripe 是一家极其复杂的全球企业，产品繁多、流程无数，所以他们定下的第一原则是：「重点不是提供 AI，而是提供正确的治理结构，让每个人都能直接去用 AI，而且确信它会帮你把事情办对。」这正是 Kai 存在的理由——治理不是给 AI 套枷锁，而是让 AI 能被信任地交到一万人手里。

### 2. 个性化上下文：Kai 知道你「是谁」，但权限由你开关

Kai 开箱即用就知道你是谁、你在组织架构图里的位置，以及今天几号、现在几点。在此之上，接入的标准工具能连到项目管理系统，弄清你参与的 OKR、最近发布的邮件、你身上的所有项目；如果你主动允许，还能连 Google Drive 和 Slack 私信。但 Sharadh 强调边界必须严格：「我们允许大家自己选择给 Kai 开放多少权限。」他本人就是关权限派——「我自己其实就是其中之一，我每次对话、或者每天都会把权限开开关关。」这种「终端用户可控的上下文引擎」，是 Kai 与外部通用聊天工具最大的差异之一。

### 3. Project 是治理单元，也是最强的意图信号

Kai 里被 Sharadh 反复强调的概念是「Project（项目）」——所有 Stripe 员工都能创建，且全部公开，有的项目 500 人、有的只有 5 人。Project 的第一身份是治理机制：由某个人决定为了让 AI 良好运转需要提供哪些东西、设置哪些安全控制，比如指定默认模型，「我们甚至不想让他们用那些超贵的模型」以控制 token 花销。但它同时是极强的意图信号：上下文引擎只是被动感知，而 Project 相当于用户主动告诉 AI「我打算做什么」。Sharadh 喜欢的一点是「我们可以让少数几个对 AI、以及成本/性能/延迟权衡非常了解的人来为大家搭好台子，其他人直接去用就行」。

### 4. 数据查询的三层分流：分析层 → 标准仪表盘 → 数据目录

Kai 做数据查询的路径，是数据科学家为人类设计、却意外极度适配 agent 的一套降级体系。Sharadh 拆解 Ask Data 这个 skill 的逻辑：先用官方认可的分析层（真正关键的指标都在那里），找不到就去看所有标准数据仪表盘、复用上面的查询，还不行才退到数据目录去搜索高质量数据集、搞清怎么用，最后自己写查询。他解释了为什么这套对人类的分流对 agent 同样有效：「事实是，在逻辑推理这块 agent 也有同样的问题，他们能回答问题，但他们根本不知道这到底是不是正确的查询、正确的表。」这些投入在帮忙把关上发挥了作用。

### 5. 数据基础设施的韧性，是数据 agent 的前置条件

Hubble 是 Stripe 内部的数据查询层，Trino 是数仓侧的查询引擎，团队在「提高它的弹性方面投入了很多」。原因很实在：Claire 总结得犀利——「因为拿不准的时候，agent 就会直接暴力轰鸣」，而 Sharadh 完全同意：「agent 在搞垮基础设施方面可有创意了。」所以让 agent 能疯狂压榨数仓却不至于把它打垮，是一项不炫酷但决定成败的基建投入。Claire 借机点出 Stripe 之所以能从 AI 里获益这么多，是因为在 AI 之前他们就一直在投入开发者体验、开发者平台、数据平台、分析层——「对人类好，对 agent 也好，这才是能让你跑起来的东西。」

### 6. Agent 身份、降级与故障模式放大

Kai 全部托管在云端、全天候在线、处于标准安全边界之内，全部运行在安全沙盒里——「它不跑在你的笔记本电脑上」。沙盒要解决的是隔离问题：Claire 的会话和我的会话不能互相干扰。Sharadh 提到一个尚未完全解决的难题是「agent 的身份」：如何界定「这是一个 agent」以及它在基础设施里穿梭时想要的权限是什么，并据此设计优先级和降级机制。他的判断非常坦白：「agent 会直接放大你所有的故障模式」，而且「我也不会宣称我们完全没出过问题」——早期确实有 agent 失控、有 agent 差点把核心系统搞垮，只是及时发现并把系统加固好了。

### 7. Skill：从「随手聊聊」到「能挑大梁的工作流」

演示的高潮是把一次性的会话打包成可复用 skill。Sharadh 说，Kai 里大家最爱的功能之一，是你做出一个仪表盘后不必每次重建、每次搭进去一堆 token 和时间，而是让 harness 自带的 skill 创建器「从这次会话中、从跟我的交互中，学到的所有东西都提取出来，整整齐齐打包成一个我随时都能调出来的东西」。这一点是 Agent 从聊天玩具变成生产力工具的临界点：「就在这个时候，AI 从一个我平时顺手在旁边随便聊聊的东西，变成了我能放心交给它去跑业务、跑工作流的东西。」导出的 skill 遵循标准开放规范，可在任何 harness 上使用。

### 8. 2,000 个 skill 的问题：检索、质量与「数量即质量」

Stripe 内部大约有 2,000 个 skill，Sharadh 坦陈「光让大家能建一堆 skill 是不够的」。难点在于：代码 agent 有天然的文件层级结构可以顺着调用 skill，但「当你在一家企业里开始工作时，你手头要做的事情根本没有什么层级结构，你经常要同时调用五套不同的系统」。所以他们投入大量精力做 skill 打包与检索、做严格的调用时机判定以维持 Kai 的表现；同时搭建平台侧自动建议机制，让每个写 skill 的人都能收到「怎么把它做得更好、怎么逐步优化」的建议。面对 telemetry 数据，Claire 一针见血：「数量几乎就是质量的一个侧面」——塞给 AI 的无关上下文越多，结果就越差。

### 9. 采用率不是靠强制，而是靠先做出 V0 给人看

Kai 的推广路径是一个典型的精简创业故事：V0 由「差不多一个人半的人力搞了两周」上线。Sharadh 说当时很难向大家解释为什么需要这个东西——周围到处都是写代码的 agent，而且可能超级强大——但「只要能把东西拿给大家看，很多问题的答案自然就清楚了」。试点阶段涨到约 200–300 用户，主要兴趣来自 GTM 团队里专门做 AI 的 Elia；随后在全公司做了一次演示，增长才真正起飞。如今全公司 86% 以上的人在用，每周一万多人使用，而负责整个体验的核心团队「依然不到十个人，而且那十个人手上同时还在忙很多别的事情」。

## 二、关键问答

**Q：Stripe 为什么要自己从头做一套 Kai，而不是直接用现成的？**
A：Claire 一上来问的就是这个。Sharadh 说 2026 年初 AI 工具迎面铺来、Claude Code 刚席卷全球，但他们很快意识到核心不是工程问题，而是「如何在大规模下复刻一家公司的运作方式」。Stripe 遍布全球、产品繁多、流程无数，所以重点不是提供 AI，而是提供正确的治理结构，让每个人都能确信 AI 会帮你把事情办对。

**Q：Kai 到底对一个人了解多少？**
A：开箱即用状态下，Kai 知道你是谁、你在组织架构里的位置、今天几号、现在几点。接入的标准工具能连到项目管理系统，弄清你的 OKR、最近发布的邮件、参与的所有项目；如果你选择允许，还能连 Google Drive 和 Slack 私信这类非常敏感的内容。Sharadh 特别强调：「对此我们确实想保持严格的边界。」

**Q：员工能控制 Kai 读到多少内容吗？**
A：能。Sharadh 说权限完全由终端用户自己选，「有些人选择不开放，我自己其实就是其中之一，我每次对话、或者每天都会把权限开开关关」。也有很多人觉得「让 AI 自己去搞定吧，上下文越多越好」。这种由用户控制的上下文引擎，是 Kai 设计上的一大特点。

**Q：为什么要建在基础 agent 积木之上？**
A：Claire 说这是「完美的吃狗粮体验」——如果你要为客户打造优秀的 agent，就应该先学会给自己打造优秀的 agent。Sharadh 认同并补充：用来构建 Kai 的一切最后都成了标准基础设施，能反过来帮 Stripe 为用户打造出色的 agent。「我们在这里做的事情，是在铺设轨道。」

**Q：Project 为什么被反复强调是治理机制？**
A：Project 是 Stripe 员工都能创建、全部公开的东西，有 500 人的、也有 5 人的。它由某个人决定为了让 AI 良好运转需要提供哪些合适的东西、设置哪些安全控制，比如指定默认模型以控制 token 花销——「我们甚至不想让他们用那些超贵的模型，因为你在这里要做的工作根本不需要那些超级模型。」这样少数懂权衡的人搭好台子，其他人直接用。

**Q：Project 除了治理还有什么作用？**
A：Sharadh 说它也是极强的意图信号：上下文引擎是被动的，而 Project 相当于用户主动告诉 AI「他们打算做什么」，这能让 AI 表现好得多。Claire 补充说她没见过有人聊过「把 Project 作为配置层和治理层」这一点，包括基于项目的模型路由、连接器、审批流等。

**Q：演示里 Kai 建仪表盘时在拉取什么？**
A：Sharadh 解释工具（tool）是「你能做的事情」，而 skill 本质上把相关工具打包起来方便找到。Kai 会自己找到 Ask Data 这个 skill——它的作用是弄清怎么用标准工具回答任何与 Stripe 数据和 SQL 相关的问题。加载这个 skill 后，Kai 就拿到了很多内部工具的权限，再用这些工具继续往下走。

**Q：沙盒是怎么工作的、为什么要沙盒？**
A：因为 Kai 不跑在你的笔记本上而是云端，Claire 的会话和 Sharadh 的会话不能互相干扰。团队搭建了安全沙盒，并给 harness 提供与沙盒交互的工具：往里安全发送数据的工具、在沙盒里搜索和执行操作的工具、以及从沙盒提取数据的工具。Sharadh 笑说「有一半的时间我自己都不知道他在做什么，我知道他是安全的」。

**Q：Hubble 是什么？团队为让数据层接入 agent 做了什么？**
A：Hubble 是内部的数据查询层，数仓侧用 Trino 作为查询引擎。Sharadh 说他们在 Trino 的弹性上投入很多，让 agent 能疯狂压榨它却不至于把它打垮；同时投数据目录和数据分层，能看到 schema 并快速提示相关数据集及用法；更高层面还有官方认可的分析层和分级降级体系。

**Q：数据查询为什么要有三层分流？**
A：因为关键指标放在分析层、标准仪表盘上有现成查询、数据目录能搜高质量数据集，逐级降级能避免乱写查询。Sharadh 强调这是数据科学家为人类理出来的路，而「agent 特别擅长摸索这一套」。真正原因是 agent 在逻辑推理上有同样的问题：他们能回答，却不知道是不是正确的查询或正确的表。

**Q：Claire 说 Stripe 能获益这么多，根本原因是什么？**
A：她说的是 Stripe 在 AI 之前就长期投入开发者体验、开发者平台、数据平台、分析层——所有那些在 AI 之前让人类在公司里极其高效的基础性投入。她常劝别人「把你 devx 团队的人数翻一倍，把数据团队的人数翻一倍，把精力花在平台投入上」，「对人类好，对 agent 也好，这才是能让你跑起来的东西」。

**Q：Agent 会怎么搞垮基础设施？**
A：Sharadh 说「agent 在搞垮基础设施方面可有创意了」，就像训练的脚本把他们教成了脚本小子。真正的应对是去思考 agent 的身份——怎么界定这是一个 agent、它想做什么、想要什么权限，并据此设计优先级和降级排包机制。他也坦白早期「有些 agent 失控了，有些 agent 可能差点把核心系统搞垮」，但及时发现了并把系统加固好了。

**Q：为什么仪表盘这种产物要能迭代，而不是生成完就扔？**
A：Claire 说真正的威力在多轮对话时才显现。Sharadh 说这不是生成完就扔在那不管的产物，「我们让大家有机会通过不断迭代自己的产物来进行深度工作，这非常强大」，对 token 效率也更好——你总不想每一轮对话都把一个 HTML 仪表盘扔掉重来。有的对话轮数挖得极深能有几百轮、跨越好几周。

**Q：为什么「最后一公里的数据处理」特别重要？**
A：Claire 说每个人的工作流差异太大，想做一个让每个人在每项工作里都能用的仪表盘实在太难，结果就会搞出无数个仪表盘，根本没法保证质量和数量。用 Kai 这样的 AI 意味着能做出轻量级应用，差不多像 Lovable 那种风格，大家自己做应用针对自己的工作流做极致优化，而且关键在于有一个沙盒让非工程师也能让 agent 写代码处理数据。

**Q：Kai 的采用率数据如何？**
A：演示仪表盘里能看到采用率曲线从相当低的数字一路爬升，「现在全公司已经有 86% 以上的人在用了，可以说是真正的人人都在用 AI」。Sharadh 说如果几周前看应该还是几百人。另外市场团队「全员 100% 都在用」，因为「我认识的市场人里，就没一个是不想做某种应用或者某种仪表盘的」。

**Q：团队规模到底多大？**
A：Claire 猜 20 个工程师，Sharadh 说「绝对不是 20 个工程师」。V0 是一人半的人力、约两周上线；试点阶段 200–300 用户时是两三个半人；现在每周一万多人在用，负责整个体验的核心团队依然不到十个人，而且这十个人手上同时还在忙很多别的事情。他同时把功劳归给开发者生产力团队和 AI 编码 agent 带来的生产力。

**Q：做 skill 是怎么从一次会话变成可复用工作流的？**
A：Kai 有一个类似 skill 创建器的 skill（harness 自带），它介入进来，把这次会话中、从跟用户的交互中学到的所有东西提取出来，整整齐齐打包成一个随时能调出的东西。可以保留为仅自己可见，也可以推到 Project 或区域里共享。Sharadh 说这是 AI 从「旁边随便聊聊的东西」变成「能放心交给它跑业务」的临界点。

**Q：导出的 skill 长什么样？**
A：像标准的开放规范 skill，「你可以在你的任何 harness 上用」。它已经帮用户把描述填好了，也填好了「Kai 可以在什么时候用它」，这一点在检索时很重要。Claire 很喜欢这种草稿式的 skill 编辑器，可以去测试、编辑、优化和管理，「只要稍微做一点提升体验的界面，效果就会大不一样」——团队投入很多让它感觉像一个 IDE。

**Q：为什么企业里 skill 检索比在代码仓库里更难？**
A：Sharadh 解释：写代码的 agent 在代码仓库、文件夹里工作，手头的事情自带天然层级结构，可以顺着层级调用 skill；「但当你在一家企业里开始工作时，你手头要做的事情根本没有什么层级结构，你经常要同时调用五套不同的系统。」所以他们做了一套非常严密的流程来判断合适的时候该调用哪些 skill。

**Q：有多少 skill，怎么保证它们不烂掉？**
A：大概 2,000 个 skill。因为上下文就是一切，无关上下文越多结果越差，所以 Claire 说「数量几乎就是质量的一个侧面」。Telemetry 显示：约 50 个 skill 是全公司每天都高频调用的，另有 100–150 个是组织架构里的细分分支在用，还有一大堆只有两三个人在用的。团队用 ETL 管道给 harness 负责人提供参考，决定哪些 skill 提拔进通用工作流、哪些移出，以免白占上下文。

**Q：平台怎么帮大家把 skill 写好、维护好？**
A：平台内置了自动建议，每个编写 skill 的人都会收到「怎么把自己的 skill 做得更好、怎么逐步优化」的建议。Sharadh 说因为允许任何人发布共享 skill、别人都能拿去用，所以提供工具让这些 skill 保持最佳状态就变得非常重要——「一旦引入了共享和企业级质量管理政策，全都变得非常重要」。

**Q：企业里只有一个通用 agent 够吗？**
A：Sharadh 说 Kai 表面看像单一产品，「它真不是，它就像多层蛋糕顶上的糖霜——每一层都可以定制」。Project 里有个「设置」功能，你甚至可以用一个自定义 agent 来驱动你的 Project，不一定非得用 Kai；后端可以由不同的 API 和不同的 harness 支持。他说企业里聊 AI 一定有多样性，「分层构建就能让我们提供最大的杠杆和可定制性」。

**Q：Human in the loop 是怎么落到 Project 层面的？**
A：Sharadh 用 HR 团队举例：处理大量敏感信息的人肯定不想让 agent 擅自把敏感数据放进所有 Stripe 员工都能访问的公开 Google 文档，但也不能因此什么工具都不给用。Project 允许针对这个工作流设定工具策略，某些工具触发 human in the loop 确认。他演示里配了一个「帮我创建一个明天太平洋时间上午 11 点的日历邀请」的例子，并强调「我也不想让 Stripe 的每个人都经历这个，那样会带来挺多阻力的」。

**Q：企业该自建还是买现成的？**
A：Claire 说现有工具可能允许在个人层面配置权限，但配置完就应用到每个会话、没结合你正在做的事情的上下文，也没法在不同用户之间共享。她自己团队做东西的好处是真能为定制用力、同时把复杂性在最终同事面前藏起来。Sharadh 补充：还要问自己「这会给每个人的日常工作带来多少合理或不合理的阻力」，因为「如果你把太多阻力摆在大家面前，他们就会去干不安全的事」。

**Q：Sharadh 提到的「降级」和「agent 身份」是怎么关联的？**
A：云端运行的 agent 会在基础设施里到处穿梭干活，所以必须想清楚它想用的权限到底是什么，并以此思考优先级、降级和排包。Sharadh 承认这一点「我们还没完全解决」。他还把它和采用率联系起来：因为 agent 会放大所有故障模式，所以沙盒、工具策略、human in the loop 这些机制必须默认到位，而不能指望每个员工自己把关。

**Q：有什么经验是「反直觉」的？**
A：最反直觉的是：做数据 agent 最该投的不是产品开发，而是基础设施。Claire 说大家问「我该怎么做才能用 AI 交付更多产品」，她回答的是把 devx 团队、数据团队的人数翻一倍。第二点是 agent 的韧性投入——「性能上的投入不炫酷，不是大家在做这些数据 agent 时会想到的东西」，但它能让 agent 极其高效地干活，因为你不必担心数仓被猛轰搞垮。

**Q：Sharadh 个人在工作之外用 AI 做什么？**
A：他笑说自己挺无趣的，但先讲了最有用的一个：帮他在六岁儿子面前显得没那么笨——孩子到了会问系外行星、遥远星系的阶段，他就拿手机查了再装作自己知道答案，「所以他帮我维持住了在他心目中爸爸什么都懂的形象」。工作方面，他有一套用 AI 确保自己不漏掉事情的完整工作流，基本把 Kai 当个人助理用。

**Q：AI 不听话的时候他会怎么办？**
A：他开玩笑说潜意识里有点怕 AI 摸清情况、知道他住哪之后会怎么对付他，所以一直挺客气的。他会说「嗨，这不是我想要的，来，我再说一遍」，可能全用大写字母，但不喜欢冲 AI 大吼大叫，「感觉就像是在冲做这个 AI 的那些人大喊一样」。Claire 把这总结成「温和育儿法」：「我知道你可以做得更好，我相信你，我没生气，我是失望。」
